# 约束优化和分层降级

核心是：在“大模型窗口 减去 输出预留”这个硬约束条件下，让模型当下真正需要的信息尽可能在场；压缩是让被裁掉的早起信息以摘要形式重新在场，蒸馏则是把跨会话常量上移为常驻上下文--持久化到MEMORY.md文件中。即裁减无损但临时、压缩有损但持久、蒸馏跨会话常驻，其实都在回答同一个问题：下一轮请求该放什么信息。

## 1. 3个功能的设计机制和触发点

### 1.1 裁剪 trimming

把本轮装不下的历史信息临时剔除，仅在当前这一次请求中有效，而且不会写入到***.md文件中，根据本地的token预算，在每次调用SendMessage/ChatStream中同步调用。

- 预算公示：(context_assember.go:127): budge = context_windows - OutpurReversed(1024) - max(set(system), reverse_token_floor) - est(本轮用户消息); if budget <= 0 -> 取 0，本轮不带历史（不能硬塞进去而把请求顶出窗口）
- 算法(trimHistoryItems):从最新往旧累加，超出budget即停。三条纪律：
  - 裁剪点必须落在组边界（以user消息为起点，含其assistant/tool消息） -> 绝不切散assistant(tool_calls)与tool结果；
  - 保留区必须以user消息开头，不能以orphan的assistant/tool开头
  - 极端情况下至少保留最新一条user消息
- 产物：AssembleResult{Trimmed,DroppedFrom,DroppedTo,DroppedCount,NeedCompaction} --- "被裁区间"就是压缩的输入；
- 工具循环内另算FitMessage：每次请求LLM之前再贴合一次窗口，因为工具结果回填会持续挤压上下文

触发点：

trimming的触发点有两个，都在关键路径上、且同步，分别是：

- SendMessage/ChatStream -> assembleChatContext -> AssembleContext,每轮开局一次；
- completeChat -> runToolLoop/streamToolLoop -> ctxmgr.FitMessage，工具循环内每次LLM调用前一次

### 1.2 压缩 compaction

将memory_******.md文件中因为context window过小要剔除的区间浓缩成一条摘要记录，将压缩后的内容标记为summary记录，且会在相应的memory_*****.md文件中添加标记为summary的记录。

AssembleContext中按照covers跳过原文 + 摘要进system，而且需要调用LLM（根据compaction mode，若是默认，则条用一次LLM，若是safeguard则调用LLM多次）。

- 压缩的机制：

  - 形态：一条## [N] summary | <时间>记录，正文首行 covers:A-B + 摘要文本；追加到memory_****.md文件末尾

  - 一条 ## [N] summary中N表示序号，序号只增不减、永不重排/复用（因为t_turn.chat_index/resp_index）存的就是历史序号 -> 因此，压缩不能改写序号，只能新增；

  - 执行流程（MemoryService.Compact,10步）：可用性校验 -> 区间合法性 -> compactionTargets(剔除已被摘要覆盖的) -> safeguard降级 -> Append(...,hintIndex=0) -> 记录节流结果 + 日志。

  - 读取闭环：context_assembler.go文件中 splitSummaryAndActive函数中建立coverd集合 -> 被覆盖的记录不回放；摘要折进一条system消息末尾（标题为：## 历史摘要，避免“非首条system”兼容问题，且受reverse_token_floor预留保护）；多条摘要按序拼接，后被前者覆盖的旧摘要自动失效。

  - 幂等/并发/失败：covers跳过 + 锁内二次确认+同会话串行；失败不写文件仅记录日志；

- 触发机制：一个触发源 + 4到闸门

  - 触发时机为什么在轮次收尾：压缩需要“本轮装配才知道的裁减区间”，且必须等本轮已落库（ReadRecords要读到本轮）；因为本轮对话已经结束，因此可以采用异步模式。
  - 节流判定点必须在“确实要发起尝试”之后

  ![](/Volumes/Wisdom/MyIdea/CClaw/document/技术难点特点/compaction.png)

压缩：NeedCompact = 正确性 + 收益 + 预算

- 只有超出context window，掉出去的记录、再也回放不到的记录才需要被摘要代表。提前压缩是有害的（拿摘要替换还能回放的原文 = 白丢信息、预算收益为零）
- 收益维度：被裁区间体检 >= hCommon.MinCompactionSrcRunes(=SummaryMinRunes,同源推导：源 < 400时摘要上限被抬到下限，压完不会更小，纯烧一次调用)。提及用hCommon.RecordsRunesInRange(records,from,to,limit)早退扫描算法，且records复用装配港独回的那份 -> 请求路径 0 IO。
- 预算维度：SummaryTextoverBudget(result.Summary)为真时不压缩，先让合并把摘要整理下来 -- 否则system单调递增 -> 历史预算更小 -> 裁更多 -> 再压，就是那个正反馈。被裁记录一直在文件里，下一轮仍是同一批，最多延迟一轮，不会漏。

### 1.3 蒸馏(Distillation)

把跨会话有效的事实沉淀到Agent的长期记忆中，即将蒸馏之后的结果写入到Agent的系统MEMORY.md文件中，写入之后将会作用到该Agent的所有会话。

为了得到蒸馏的结构，必须调用一次LLM，通过节流阈值控制频率。

- 蒸馏机制
  - 输入：plainRecords(records)过滤掉summary记录，只取原始对话，len < DistillMinRecords(6)直接返回
  - 目标：MemoryDocPath(agent) 即agent对应的MEMORY.md文件必须已经存在，=
  - 产出：追加一个时间戳的小节 ## <yyyy-MM-dd HH:mm:ss> | session <sessionId> + 最多 DistillMaxFacts(8) 条事实(facts,每条fact的大小 <= DistillMaxFactRunes(200))；LLM会判断“没有有长期价值”则会输出 NONE -> 不写文件；
  - 有界：从memory_****.md文件中读取的最大读取20000字符数，即从最旧开始裁减
  - 原子写：临时文件+rename机制，保障将蒸馏结果写入到MEMORY.md
- 触发点
  - 与压缩同一个后台任务triggerMemoryMaintenance，一轮一个routine,共享同一次ReadRecords(从memory_***.md文件中读取出来并解析后存入到MemoryRecord struct中
  - 条件：turns >= DistillMinTurns(6) 且 DistillIntervalTurns(10) == 0;turns来自 TurnCount= Max(t_turn.seq)，即每轮对话落库后 + 1
- DistillPresure设计机制
  - 这是调度信号，不是蒸馏输入 --- 不参与“蒸馏什么内容”（蒸馏内容是由Distill内按水位重新取批次 + 预筛 + 窗口前缀决定的），只回答“现在值不值得为它花一次判断/一轮蒸馏”
  - 蒸馏的判断是根据是否达到蒸馏的门槛（6 turns）,以及轮次是否是10的倍数turn次，这就会造成未到10的倍数的轮次时产生尾巴，为避免这些尾巴被消费掉，DistilPresure就是这个问题的解，因为难点在于“这个判断在请求路径上，不能为了它增加IO，也不能做全量统计”。那么数据来源：***assembleChatContext刚刚读回的记录快照，经maintenanceRequest.records传入进来 ***。那么工作原理是什么呢：
    - 水位时权威索引，watermark来自MEMORY.md里的会话水位。pending = record.Index > watermark && !IsSummary() --- 摘要记录被排除，因为它是压缩产物，不是蒸馏输入
    - 口径刻意比Distill的输入“宽”，它不排除“已被摘要代表的记录”，为什么：
      - 精确口径要调ActivePlainRecords （建map + 全量扫，实测2000条 = 137 us/341 KB）,而这在请求路径之上；
      - 多算的后果仅仅“可能多触发一次”，而Distill内部还会再卡三道（记录门槛数、hasDurableSignal预筛、窗口前缀） => 多触发 = 几微秒的判断，方向安全
      - 早退封顶：pendingChars >= DistillMaxInputChars就停，因为下游只问“够不够一个批次”，不需要精确总量---于是记录条数再多，成本也恒定（实测 200/2000/20000条耗时基本一致，35-80us全部来自路径解析 + 那次笑文件读，不扫描）

### 1.4 三者写作与“共同原则”

一轮的生命周期：装配 -> 裁剪(同步,必须) -> LLM -> 回复 -> 落库 -> 触发后台维护

​															|_压缩(条件:本轮裁剪发生了)

​															|_蒸馏(条件:轮次跨过 10的倍数)

下一轮：裁剪重算(与压缩无关) + system里可能多了摘要(压缩的成果) + MEMORY.md可能多了事实（蒸馏的结果）。

- 裁剪是硬约束，确保不超context window，压缩是信息保底(保“裁掉的别真丢”),蒸馏是跨会话沉淀（确保换个会话还记得）
- 三折都不改变已经将回复发送给客户的事实，压缩/蒸馏失败只记日志（旁路原则），裁剪失败就是上游超窗报错
- 裁剪不是压缩的一部分，它是压缩的前置信号源，裁剪的目标是本次请求不超context window

## 裁剪

### Q1(F1) 预算连"最新一条消息"都放不下时，会不会退化成"一条都不裁"？而这时压缩还会触发吗？

**A：会退化成全量，而且压缩**不会**触发——这是同一条链上的两个后果。**

- 现象：`trimHistoryItems`（`ctxmgr/context_assembler.go:389`）在预算极小时命中"保底分支"`if cut <= 0 { return items, nil, total }`（`:420`）——kept=全部、dropped=空。
- 触发条件（比想象中常见）：需要 `items[0]` 是 user 记录、之后**再没有** user 记录，即"用户只问了一次、随后几十轮工具调用"的单轮长任务会话；此时对齐步骤把 `cut` 推到末尾，回退搜索"最新一条 user"就落到 index 0。
- 连锁后果：`dropped` 为空 ⇒ `Trimmed=false`、`DroppedFrom=0` ⇒ `NeedCompact` 直接返回 false（它要求 `DroppedFrom>0`）⇒ **预算超了却永不压缩**；同时 `KeptHistoryTokens` 只报了最后一条的量（`total` 在对齐后不再重算）。
- 原因：`total` 在累加循环里算完后，后续两步"组对齐"会改 kept 集合却不改它；"整体退回"是有意保底，但把"超预算"这件事吞掉了——而上层判断压缩与否**只**依赖 dropped 信号。
- 建议：(1) 组对齐之后重算 kept 的 token；(2) 把软上限兜底显式化（如 `AssembleResult.NewestGroupOverBudget` / `OverflowTokens`）并纳入 `NeedCompact`。
- 为什么更好：压缩的触发信号是单点的，单点被静默 = 静默退化。这个值本来就算得出来，只是没往上抛（`ctxmgr/budget_cap_test.go` 已把 `Kept ⊆ Budget` 当不变量断言，说明契约就是"准确"）。

### Q2(F2) 调小 `max_history_tokens` 能"更早开始压缩"吗？

**A：只在最新一条消息不太大时成立。**

- 现象：`trimHistoryItems` 的循环守卫 `i < len(items)-1` 使**最新一条永远保留**，哪怕它自己就超预算；字段注释也自认"软上限"。
- 数量级：一条 30k rune 的助手回复 ≈ 20k token。设 `max_history_tokens=8192` 就是 2.4×，设 2048 可达 10×+（再叠加 Q1 的分支还会让报告值失真）。
- 原因：保底语义与预算语义挤在同一个 `budgetTokens` 里，溢出量没有单独建模。
- 建议：给单条回放加长度上限（与 `ToolReplayMaxRunes` 同风格的 `MaxHistoryItemRunes`，对超长回复做首+尾截断）；至少把超限倍数打进日志与 `AssembleResult`。
- 为什么更好：`max_history_tokens` 是唯一暴露给运维的压缩节奏旋钮，它在小值区间失效不会报错，只体现在账单与延迟上。

### Q3(F3) token 估算是保守的吗？

**A：对 CJK 保守，对其它语种/机器文本偏乐观；而它同时决定"裁剪多少"和"输出要多少"。**

- 现象：`EstimateInputTokens`（`ctxmgr/token_budgeter.go`）把非 CJK 一律按 4 char/token；`pCommon.IsCJK`（`platformutility/common/string_utility.go:165`）只覆盖汉字/假名/谚文。JSON、base64、十六进制、西里尔/阿拉伯/泰文通常落在 1.5~3 char/token，即被低估 1.3~2.7 倍；全局只有 ×1.2 一档余量。
- 更关键：`DynamicMaxTokens`（`token_budgeter.go:138`）用同一个估量**顶格**算 `window - est(input)`，于是 `est(input) + max_tokens` 恰好贴住窗口，零余量。
- 后果差异：裁剪侧低估只是"少带历史"（柔性）；输出侧低估是**上游直接拒请求/截断**（硬故障，且在用户可见路径上）。
- 建议：估算对非 CJK 非拉丁采用更保守比值（或对疑似机器文本单独下调）；`DynamicMaxTokens` 额外受 `OutputReserve` 约束，让"预留"与"实际要的额度"同源。
- 为什么更好：把一个硬故障的概率绑在两个软参数上，是当前设计里最容易"换模型就炸"的地方。

## 压缩

### Q4(F6) 进入"摘要超预算"状态后，历史还会被压缩吗？

**A：不会——而且这是一条可能永久停住的路。**

- 现象：`NeedCompact` 要求 `!SummaryTextOverBudget`，`NeedMerge` 要求 `SummaryTextOverBudget`（`token_budgeter.go` 内两者互斥）。进入该状态后不再产生新摘要，而历史仍在被裁：**这些记录既不在回放里，也没有摘要代表**。
- 卡死条件：合并的约束很严——`mergeCandidate`（`mstorage/compaction.go:245`）要求区间内不存在"不属于本集合的摘要记录"且 `verifyCovers` 通过，任一不满足即返回 nil；此时只剩 WARN，没有任何兜底。
- 原因：两个机制用同一个"总量"标尺做互斥决策（方向本身正确，防正反馈），但**没有任何一方能在自己无法推进时兜底**。
- 建议：给合并一个"降级放行"（保留率下限从 0.5 放宽到 ~0.35 并标 degraded）；或允许 `Compact` 在摘要超预算时继续，条件是新摘要 rune **净小于**被覆盖原文 rune（那一步一定让 system 变小）。
- 为什么更好：把"卡死（持续丢信息 + 可能持续烧钱）"降级为"质量下降但不丢信息"。

### Q5(F7) `covers: A-B` 宣称覆盖的区间，真的是模型看过的全部内容吗？

**A：不是——每条记录只送进模型的**前 2000 rune**。**

- 现象：压缩与蒸馏送入模型的行都由 `compactionPromptLine` 渲染，正文被 `hCommon.MemoryExcerptRunes = 2000`（`harness_common.go:252`）截断；而 `covers` 是"整条记录已被代表"的承诺，读取端无条件信任它。
- 数量级：一段 3 万 rune 的工具输出，只有前 2000 rune 进过模型，其余在摘要里没有任何表示，却已经退出回放。
- 原因：成本有界（单条上限）与承诺精确（区间）冲突时选择了前者，但**没有把差距显式化**。
- 建议：长记录渲染成"首 + 尾"（结论/错误信息常在尾部）；或在摘要正文标注"来源已截断"，并把截断条数放进 `CompactionResult` 以便观测。
- 为什么更好：这是**系统性**（非偶发）的过度声明，方向和"丢最新最值钱的那段"一致；至少要做到可见。

### Q6(F8) 同一件事在不同地方用的度量口径一致吗？

**A：有两处不一致，都在阈值附近才咬人。**

- `hCommon.RecordsRunes` 不 `TrimSpace`，而 `SummariesRunes` 会（`memory_record.go`）——同一个文件里两套计数；
- 合并的**触发判定**看注入文本（`AssembleResult.Summary`，含 `"\n\n"` 连接符），而**动作门**看文件记录（`SummaryOverBudget(records)`）——两者差着连接符与空正文过滤。
- 建议：收敛到同一个函数（例如都走"生效摘要的正文 rune 和"），并让触发与动作共用它。
- 为什么更好：阈值附近的口径漂移会产生"判定说该合并、动作说没超"的日志，是最难查的一类不一致。

## 蒸馏

### Q7(F9) `MEMORY.md` 的体积会随时间只增不减吗？

**A：条目有上限，**水位表没有**——后者是唯一"随时间必然变坏"的维度。**

- 现象：`watermarks=sess:idx,sess2:idx2,…` 被渲染成**一行**（`mstorage/distillation.go:697`），每个蒸馏过的会话都会加一条（约 25~40 rune）；而 `DistillMemoryDocMaxChars = 12KB` 只约束条目（`fitFactsBudget`，`distillation.go:488`），**不含水印行**。
- 后果：共享文件的会话数单调增长；上千会话后这一行本身就吃掉/挤爆 MEMORY.md 的注入预算。而 MEMORY.md 在注入顺序里**最后**，被截断时从尾部切——那一行超长会把后面的 facts 一起挤掉。
- 原因：水位与条目共用一个块（为了原子性与纯文件自描述），只有条目那一半设了上限。
- 建议：给水位表设条数/字符上限 + 淘汰"最久未见"的会话。淘汰代价极低：最坏情况是那个会话的尾巴被重复蒸馏一次；历史文件若已不存在，`pending` 为空，**零成本**。或者把水位移到同目录 sidecar（会牺牲纯文件自描述）。
- 为什么更好：唯一一个"不处理就一定会超窗"的维度，且修复成本很低。

### Q8(F10) 会话前几轮会被蒸馏保护吗？

**A：不会。** `NeedDistill`（`ctxmgr/token_budgeter.go:229`）在 `turns < DistillMinTurns(6)` 时恒为 false，前 5 轮完全没有长期记忆保护——而这几轮恰恰包含需求、口径、路径这些最该进长期记忆的内容（也正是 Q1/F4 修复前最容易被压缩吞掉的那批）。
更为难的是：注释与设计声明都写着"轮次节拍只是**速率上限**"，但实现里它同时充当了**触发条件**——声明与实现不一致。
- 建议：让**内容**成为唯一硬门槛（`PendingChars >= DistillMaxInputChars` 已具备），把 `DistillMinTurns/DistillIntervalTurns` 降级为"两次触发之间的最短间隔保护"；`closing` 语义不变。
- 为什么更好：与代码自己的设计声明对齐，同时缩小"开局无保护"的暴露窗口。

### Q6(F12) "攒够一轮就提前蒸"里的"够"和"这一批装得下吗"里的"装得下"是同一个量吗？

**A：不是（本轮审计新发现）。**

- 压力侧 `distillPressureAt`（`memory_service.go:523`）累加的是 **原文正文** rune：`TextRunes(records[i].Content)`；
- 选批侧 `windowPrefix`（`distillation.go:186`）累加的是 **送审行** rune：`compactionPromptLine(rec)`——含 `[i] role: ` 前缀，且正文被 `MemoryExcerptRunes(2000)` 截断。

同一条记录在两处的"体积"可以差一个数量级（长工具输出），于是两个判断各用各的口径：
- 长记录占多数的会话 → 压力**高估** → 触发一次实际很小的批（多花一次 LLM 调用）；
- 纯短记录的会话 → 压力**低估** ~12 rune/条 → 触发略晚（可能少蒸一点）。

- 建议：压力侧改成与送批同量级——`pendingChars += min(TextRunes(content), hCommon.MemoryExcerptRunes)`（不建字符串，保持"够一轮就早退"的便宜特性）；或直接复用 `compactionPromptLine` 的长度（严格同源但略贵）。
- 为什么更好：这两处是**同一个判断**（"攒够一轮了吗"）的两端，口径不同会让阈值失去意义；而且修法只在压力侧改一行，不触碰蒸馏本身的语义。

## 协同

### Q10(G1) 三份"会变大的 system 内容"有总量账本吗？

**A：没有。** system 里同时有：启动文档（受 `BootstrapTotalChars=60K rune`，在 `prompt_service`）、历史摘要（受 `MaxSummaryTotalRunes=12000 rune`）、MEMORY.md（受 `DistillMemoryDocMaxChars=12KB`，又被启动文档总预算截断）。三者各有局部上限，**但没有一处知道总量**；`SystemPromptReserveTokens` 是静态值，真实 system 增长只表现为"历史预算被挤压"——即 `est(system)` 变大 → `Budget()` 变小 → 裁得更狠 → 压得更多，**正反馈**，且完全不可观测（`AssembleResult` 只有一个 `SystemReserveTokens`）。
- 建议：把 `est(system)` 拆成三段（bootstrap / summary / memorydoc）放进 `AssembleResult`，并把它作为 `NeedMerge`、`NeedDistill` 的显式输入（例如"system 段超阈值时禁止任何增加 system 体积的动作"）；`PolicyWarnings` 也可从"配置静态检查"升级为"运行时趋势告警"。
- 为什么更好：三个机制的最优解彼此耦合（压缩用 system 空间换回放、蒸馏用 system 空间换跨会话记忆），只有同一个账本才能判断"这次动作是否净收益"。

### Q11(G2) 三个触发谓词之间还有哪些盲区？

**A：F4 修复后，压缩已能感知蒸馏水位；剩下的盲区是"计划不带理由"。**
现状：`maintenancePlan` 只有三个 bool，没有"为什么"——事后无法从日志/结果回答"这一轮为什么没压缩"（是被节流？收益不足？还是被水位钳住？）。
- 建议：让 plan 携带 why（哪个谓词触发、被哪个上限拦住），并一并进入日志与测试断言。
- 为什么更好：本轮的三个新日志（clamp/defer/force）已经证明"能说清决策"对排障的价值；把它结构化是自然的下一步。

## 性能

### Q12(P1) 每轮装配里最贵的部分是什么？

**A：`hCommon.CoveredIndexes`（`memory_record.go:150`）——它按 **covers 区间长度**建 `map[int]bool`，每轮请求都会重建一次，随会话寿命线性增长。**
另外 `SummariesOf` 每轮被调用约 4 次（`splitSummaryAndActive` / `ActiveSummaries` / `ActivePlainRecords`），每次都分配一个新切片。
- 量级：实测 79 条记录 → 回放 11,972 token，单次装配在百微秒级，当前不是瓶颈；但 5000 条记录的会话会让这张 map 达到 5000 项。
- 建议：摘要的 `covers` 天然有序 → 改成区间游标/二分判断"某序号是否被覆盖"，可去掉整张 map；`SummariesOf` 的结果在一次装配内复用一次即可。
- 为什么更好：请求路径上的成本应当是常数级或与"回放量"成正比，而不是与"历史总长度"成正比——后者只增不减。
