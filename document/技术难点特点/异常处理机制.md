# 异常处理机制

## 1. 哪些上游异常可恢复

通常情况下，有以下异常通常会被定义为可恢复：判断是否为可恢复异常的入口函数是cclawservice/exception.IsRetryableLlmError实现判断，依据是类别 + 状态码：

| 上游返回                | 类别                     | 可重试 | 依据                                  |
| ----------------------- | ------------------------ | ------ | ------------------------------------- |
| 429普通限流             | rate_limit               | Y      | LlmCategoryRateLimit                  |
| 500/502/503/504/529     | server                   | Y      | Category==server && StatusCode >= 500 |
| 链接失败/链接重制/断流  | transport                | Y      | StatusCode==0                         |
| 流中空闲超时（60s）     | transport                | Y      | 同上(NewLlmStreamTransportError)      |
| 401/403/404             | Auth/forbidden/not_found | X      | 配置,重试无意义                       |
| 400/422                 | invalid request          | X      | 参数/上下文,重试无意义                |
| 402/欠费/quota out      | quota                    | X      | 需充值                                |
| 内容安全拦截            | Content_filter           | X      | 需改输入                              |
| http 200, body 带error  |                          | X      | StatusCode==200,排除                  |
| 客户端主动终止          | ---                      | X      | ErrRequestCanceled/Context.Canceled   |
| 空流/空choices/校验失败 | RuntimeClientError       | X      | 非*LlmStatusError                     |

- Emitted 守卫，chatCompletionStreamOnce/streamWithToolOnce在首次调用onChunk/onReasoning/onToolIntent时置mitted=true;一旦为真,即使错误可重试也立即返回不再重试，避免重复内容

## 3.恢复系统运行的机制

### 3.1 请求内自愈（in-request recovery)

1. 重试成功即完全恢复：同步路径 （doCompletion/CompletionWithTools) 无emitted约束，可放心重试；流式路径在首字节前同样可重试；
2. 空闲超时 -> 终止 -> 重试：把卡斯的流转成可重试的传输错误，上游恢复即成功
3. 工具循环自愈：工具执行失败不引发失败请求，而是把{"error":...}回填给模型重新决策，最多AgentToolMax=30轮
4. 路由降级：LLM分类失败。超时 -> 静默回默认Agent
5. 并发等待，每个Agent闸FIFO等待最多AgentGateWaitTimeout=30s,容量释放后自动继续

### 3.2 系统级恢复(短板)

1	无熔断器	上游持续 5xx/429 时，每个请求仍各重试 3 次 → 对已过载的上游放大 3× 出站压力（多实例再 ×N），可能把"慢"拖成"雪崩"
2	无 provider 运行时故障转移	resolveProvider（chat_service.go:345）只是"选择第一个可用的 PrimaryModel/Fallbacks"，选中后调用失败不会切到下一个 provider；Fallbacks 形同虚设（只有启动期选择作用）
3	不遵从 Retry-After	429/503 常带 Retry-After（秒或 ms），当前固定 500/1000/2000ms，可能过短（继续被限流）或过长
4	退避无抖动（jitter）	固定指数序列 → 并发请求同频重试，形成同步脉冲
5	无全局重试预算 / 错误率闸	重试不受全局速率约束（本服务入站 TrafficFilter 只看入站 IP+API，管不到出站重试）
6	无健康状态记忆	不记录"某 provider 连续失败"，无法跳过已知故障 provider，也无运维告警/自动摘除
7	无部分回答续写	emitted 后错误即终态（仅发 notice{incomplete} 提示"可能不完整"），只能用户手动重发，不能从断点续生成
8	空流不可重试	empty stream content 归 RuntimeClientErr（非可重试），但它常是上游瞬时抖动，是可重试候选
9	重试占用并发槽	重试发生在已持有 3 道闸之后，退避期间仍占槽 → 加剧 ChatBusyErr(503)
10	重试策略不按类别区分	429（应少重试+读 Retry-After）与 5xx（可多重试）用同一套策略
