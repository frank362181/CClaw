## 1. 用户登录缓存 single flight

在用户登录到本系统构建session时采用single flight技术方案，该方案技术特点：

- 监控请求：single flight在内部维护一个map,用来追踪当前正在处理的请求；
- 检查：当一个新的请求到达时，检查map中是否已经存在相同的key的请求正在处理；
- 分流处理：
  - 若存在则新请求不执行，而是等待，直到正在执行的额请求完成；
  - 若不存在，当前请求被标记为首个请求，去执行真正的任务
- 共享结果：当首个请求结束后，结果被保存，并同时告知所有等待中的请求已经完成任务执行，共享结果

## 2. 启动文件设计原则

建议原则：
流程规则 进 AGENT.md；价值观 进 SOUL.md；事实与记忆 进 MEMORY.md；两者不重复；当前 AGENTS.md 里 “人格/语气”类内容应下方或删除。就是说能力在SKILLS.md，TOOLS.md只是记住“有哪些能力、资源在哪里”的备忘。

- AGENTS.md: 
  - 职能：作业手册
  - 业务类比：岗位职责 + 作业制度
  - 内容定位：绘画启动流程、任务处理SOP、工具/记忆规则、安全与合规红线、输出规范；
- SOUL.md:
  - 职能：人格/价值观
  - 业务类比：职业准则
  - 内容定位：不良资产专家人设、职业道德（客观/审慎/保密）、沟通风格
- IDENTITY.md
  - 职能：身份名片
  - 业务类比：工牌
  - 内容定位：名称、emoj、头像、对外简介、版本
- USER.md
  - 职能：用户画像
  - 业务类比：客户档案
  - 内容定位：服务对象岗位/机构、术语表、项目经验、决策记录
- MEMORY.md
  - 职能：长期记忆
  - 业务类比：知识库/工作日志
  - 内容定位：各自技能用法 + 业务场景示例 + 合规提示
- TOOLS.md：
  - 职能：记录在“在哪里/用什么、模版放哪里”
  - 业务类比：工具清单、本地资源地图
  - 内容定位：记录目录、模版、命名习惯、工具清单、本地资源地图等；但并不定义具体的工具，实际的工具定义还是在SKILL.md中,在TOOLS.md中对这些TOOL进行引用

## 2. SKILL文件的设计原则

前提是某个动作或流程标准化、高频、重复性。而且，还应该：

- 稳定的过程性知识（procedural knowledge），而非普遍性知识

  skill的核心是“怎么做”--带步骤、脚本、模版、参考文档。如果只是记住项目规范、风格偏好，那属于instructions(常驻全局)，不需要做成SKILL

- 按需触发，而不是大部分工作都要用

  SKILL是on-demand的（通过description发现+渐进式加载）。若某规则适用于几乎所有代码任务->用copilot-instructions.md;只有特定任务才需要考虑SKILL

- 能否定义清晰“触发词”

  SILL依赖description被模型自动发现。如果一个动作无法用几句关键词描述“什么时候用”，做成SKILL后可能永远不会被触发（这是常见的反模式）。

- 能否真正跨多个步骤/携带资产

  判断SKILL vs Prompt的分界线：

  - 多步骤工作流 + 自带脚本/模版/参考文档->SKILL
  - 单个聚焦任务、参数化输入即可 -> Prompt（/ 里也能出现，更加轻量）

- 产出是否足够稳定

  封装成SKILL的应该是结果可预期、踩过的坑已固化的动作。还在频繁变化、试错中的流程，过早封装只会不断的来回改SKILL.md。

## 3. front matter机制

  front matter的本质：它是可选的、用来把metadata和正文给分割开来，而不是进入到system prompt的闸门。若无front matter判断机制则非常简单front matter只是负责切分，并不负责把关。

判断正文是什么 <- front matter只影响这一步

首行是"---" 且有闭合的"---"行，有front matter， "---"包裹的之间的YAML元数据剥离，只取后面的正文 进入到prompt的正文；

首行不是"---"则就是普通的md, 无front matter，整个md就是正文，进入到prompt正文的候选区

首行是"---"无闭合的"---"，视为普通的md, 整个md就是正文,进度到prompt正文的候选区，不判断为front matter

正文能否进入/进入多少到system prompt <- 由预算/空白/缺失/范围决定，与front matter无关最终决定哪些内容进步到system prompt中的判断依据是：

  - 有front matter的就取body部分，没有的就取整个文件内容
  - 然后经过：空白->预算->范围-> 三道过滤，剩下的才是真正放入到system prompt中的内容

对于启动文件来说，没有front matter时整个文件内容放入到system prompt反而是期望行为，因为AGENTS.md/SOUL.md本质就是“要喂给模型的指令”，用户写的
多长、写什么，就该让模型看到什么（只要不超预算）。

## 6. 本产品设计&技术特点

### 6.1 获取bootstrap startup files/SKILL.md

1. 系统启动时，从数据库中加载所有的LLM 、agent（支持多agent）、以及每个agent对应的启动文件信息；同时文件指纹建立缓存机制；
2. 每轮对话开始时，chat_service.go的聊天函数中调用agent_router.go进行agent的路由选择，读取agent、LLM provider信息，若文件指纹被修改，再次读取，否则从缓存中获取对应信息；
3. 确定了agent后，获取与该agent对应的SKILL.md信息，将SKILL.md信息载入到toolset中
4. 基于agent 启动文件信息、SKILL.md，构建system prompt

AGENTS.md,SOUL.md等启动文件的真正读取的点是PromptRepository.LoadWorkspace() -> 内部循环 -> readAgentDocumentLocked()。读取启动文件有两个触发时机，且因为指纹缓存，绝大多数情况下并不会真的读盘。即进程启动时，和每轮对话时。

### 6.2 压缩机制

本项目中prompt压缩机制是 3 条相互独立、意图相近的机制：

#### system prompt组装

system prompt组装期[受控快照]压缩 prompt_service.go + prompt_repo.go中实现。启动文件AGENTS.md/SOUL.md/...等启动文件并不是整篇原文进入到system prompt，而是走一条处理管线。入口是service/prompt_service.go的BuildSystemPromptEx -> assembleSystemPrompt，数据来自model/repo/prompt_repo.go，预算常量在common/cclawservice_const.go文件中定义。压缩处理流程：

1. 只注入快照，skill正文按需加载

   文档清单StartupDocFiles固定顺序为：AGENTS -> SOUL -> IDENTITY -> USER -> BOOTSTRAP -> MEMORY。SKILL.md只把front matter解析成元数据（AddSkill），正文不进prompt

2. 剥离 front matter

   utility/cclawservice_utility.go的SplitFrontMatter:只把顶部---,---包裹的yaml当作元数据（用于意图/路由判断），不进入system prompt;没有front matter的普通md，正文=完整原文（避免丢正文）。

3. 按会话范围过滤

   根据isKindAllowedInScope（normal：全量注入,包含MEMORY.md；subagent：只注入AGENTS.md；corn：AGENTS/SOUL/IDENTITY/USER，不包含MEMORY.md；heartbeat:不进入prompt）

4. 缺失/空白处理

   - 空白/纯空白正文 -> 整段跳过
   - 必须文件缺失 -> 注入[MISSING] Expected at: <path>标记，让模型知道缺文件

5. 单文件预算截断

   - 普通启动文件上限 MaxBootstrapFileChars = 20000
   - USER.md 单独MaxUserDocChars = 4000
   - 超限用common2.TruncateRunes截断（按rune，非字节），并把文件名记入truncated清单

6. 总量预算压缩

   这是最重要的，在函数prompt_service.go -> enforceTotalBudget函数实现，MaxBootstrapTotalChars = 60000；不是各个文件各自为政，而是共用一个60000总盘：按顺序累加，AGENTS.md最靠前所以优先级最高；当前section放得下就整段保留，放不下则先【截断到剩余预算】，预算耗尽尾部文件整个丢弃。

7. skill元数据目录的独立压缩

   在prompt_service.go -> renderSkillsCatalog函数中实现，数量上限是 MaxSkillsInPrompt = 150，目录字符上限MaxSkillsPromptChars = 18000；先试完整description；放不下就用二分查找压缩description长度（4～120字节区间）；最短描述仍为放不下时从尾部逐条丢弃skill

8. 截断提示

   任一层发生截断，就在末尾拼一个 ## Bootstrap Context Notice，把被截断/丢弃的文件名列给模型。

#### LLM请求级

context_window预算，在service/runtime/llm_message.go中构建请求时实现：

- BuildChatCompletionRequest 每次请求时调用dynamicMaxTokens

- estimateInputTokens:CJK 约为1.5 Bytes/token、其他约为 4 Bytes/token、每条消息 + 4 token开销、乘以 1.2的余量

- dynamicMaxTokens：max_tokens = min(ContextWindow - 估算输入，provider单次输出上限)，保证[估算输入+ max_tokens <= ContextWindow]，避免长输入超窗口被供应商拒绝

- ContextWindow = 0(未配置)时不发送max_tokens，由供应商用默认值

  这属于输出预算侧压缩，只裁剪max_tokens，不裁剪输入本身。

LLM请求级context window / max_tokens预算，run_time/llm_message.go在组装请求时实现；

#### 对话历史/上下文摘要压缩

目前只是设计了字段（compactionMode/ReverseTokenFloor），并未实现

### 6.3 Agent路由机制

多Agent来说，通过用户的问题，理解意图，选出合适的Agent是必要的，当前Agent路由机制在agent_router.go -> Resolve函数中实现：

1. 用户显式指定，即用户选择(通过UI进行选择)
2. 会话绑定，即用户在聊天界面中选择某个会话，即选中与该会话绑定的Agent
3. 关键词规则命中，数据库有表t_agent_route_rule表，定义了每个agent的关键词表
4. LLM分类，将用户的问题通过构建classify system prompt + agents的摘要发送给LLM，由LLM选出合适的agent，返回agent id;
5. 默认agent兜底

### 6.4 Chat Stream 并发机制

Golang中http/net标准模型每个请求就是一个goroutine的设计策略。不管是同步的Chat请求，还是支持流式的ChatStream，整个请求从读请求 -> 写浏览器 -> Flush整个循环都在同一个goroutine内同步完成。

当前并没有对并发进行控制，即并发上限、SSE长链接常驻、每agent并发闸都没有进行有效的控制，实际上应该要控制，原因有：

- goroutine便宜，但每请求下游都不便宜，认证=Redis+SQLite、每会话DB缓存、上游LLM式同步占用链接/额度、工具链路会exec子进程。goroutine数量并不是瓶颈，但是下游并发是瓶颈。
- SSE长链接=每链接一个长期占用的goroutine + 一个上游流（LLM）：现在的ChatStreamRegistry无上限，极端下fd/内存/上游额度一起涨，切没有背压；
- 没有"每agent"维度：默认agent比较容易被打满，t_agent.max_concurrent已经设计好，但是未应用

<u>应该要从全局并发数（保护下游）+SSE长链接数（防止耗尽）+每agent并发（业务公平+模型额度）三层闸控制并发</u>。



### 6.5 function calling机制

#### 1 当前方案

流式chunk内部解析+分片拼接，实现的方案如下：

	streamToolLoop(chat_service)                             前端 SSE
	│ for 轮次 ≤ 5
	  ├─ StreamWithTools  ── 一条上游 SSE 请求
	  │    ├─ delta.reasoning_content ────────────────▶ thinking {delta}
	  │    ├─ delta.content ──────────────────────────▶ message {reply}
	  │    └─ delta.tool_calls ─┐
	  │       toolCallAccumulator 内部攒分片 ┐ 流结束后
	  │       └──────────────► 完整 []ToolCall ◄─┘ 才返回
	  ├─ calls 非空:
	  │    onStatus("正在思考…")          ──────────────▶ status
	  │    逐个 toolSet.Exec(阻塞)       ✗✗✗ 无任何事件流向用户 ✗✗✗
	  │    回填 assistant(tool_calls)+tool(结果)
	  │    └─ 下一轮 → 再发一条上游 SSE（体验断档）
	  └─ calls 空: 把已流式的 content 当最终答复

  关键局限：

1. tool_calls分片只在流结束后拼成完整ToolCall才交给上层--工具阶段对于前端完全不可见；
2. 工具执行式静默阻塞，SSE上没有任何事件；
3. 多轮工具=多次割裂的上游请求，用户只看到“正在思考...”，然后答案突然流出。

#### 2 机制和原理
  从代码上来看，function calling实际上只是将tools的信息构建成请求并发送给大模型，这些tools信息来自于toolset.go中的LoadToolSet函数中，将SKILL.md文件中的内容给加载进来，LLM之所以能做的到function calling，流程图：

![function calling](/Volumes/Wisdom/MyIdea/CClaw/document/function-calling.png)

本质上是因为：

- 本质：模型只是“声明意图”，并不执行
  function calling 在底层不是一种让模型链接到外部的系统机制，而是：模型把“工具定义”当作可用的动作清单，在需要外部信息或执行动作时，以概率生成一段特殊结构的文本 ---
  内容是“我要调用***函数，参数是***”。然后你的运行时(本项目是：ChatService.go的ToolSet.Exec)解析这段文本、真正执行、把结果回填。
  模型 -> 意图文本 -> 运行时 -> 真实结果，中间隔着的是 业务代码。
- 为何“只发schema”就够？ --- 推理与训练
  训练侧：模型在预训练/后训练时，喂入了大量形如（对话历史 + 工具定义  -> tool_use输出 -> 工具结果 -> 最终回答）的样本。模型学习到的是：当对话里出现 tools 清单、
  且任务需要外部信息时，应该输出tool_use格式的token序列，而不是继续应答。
  
  推理侧：LLM本质上是next-token预测器。请求里的tools会被当作普通上下文token注入；当模型“觉得”该调用工具时，它在此表中选出一个特殊的控制token（如tool_use起始token）,
  然后按约束继续生成函数名和参数。整个过程和写一段回答没区别 -- 只是格式被约束定成了结构化的JSON。
  - 协议层：三个关键段
    - 请求段（生成请求）BuildChatCompletionRequestWithTool函数的作用
  
          {
            "model": "qwen3-8b",
            "messages": [ {"role":"system","content":"..."}, {"role":"user","content":"请查询杭州市天气"} ],
            "tools": [{
              "type": "function",
              "function": {
                "name": "get_weather",
                "description": "查询指定城市实时天气与未来三天预报…",
                "parameters": {            // ← JSON Schema
                  "type": "object",
                  "properties": { "city": { "type": "string", "description": "城市名称…" } },
                  "required": ["city"]
                }
              }
            }]
          }
      这个正是toolset.go从SKILL.md解析出来的Tool -> llm_message.go的Tools
    - 响应段：模型返回的tool_calls

          {
            "choices": [{
              "message": {
                "role": "assistant",
                "content": null,                        // ← 没有正文
                "tool_calls": [{
                  "id": "call_abc123",
                  "type": "function",
                  "function": {
                    "name": "get_weather",
                    "arguments": "{\"city\": \"杭州市\"}"   // ← 注意:这是字符串,需要你 json.Unmarshal
                  }
                }]
              }
            }]
          }
      两个关键点：1.arguments是字符串形式的JSON，非对象，需要应用层自己解析；2.content为null说明模型这一轮“只是调用工具不回答”
    - 回填段：tool角色消息
      执行完脚本后，把结果原样拼回对话历史，用tool_call_id关联到刚才那次调用：
      { "role": "tool", "tool_call_id": "call_abc123", "content": "{\"city\":\"杭州市\",\"current\":{...}}" } -> 本项目的示例
      对应到llm_message.go的ToolResultMessage(callId,content)。注意：messages必须严格交替为带上执行结果，否则模型会困惑。
#### 3 为什么必须“工具循环”（agent loop）
  因为模型一次只能表达一步意图，而是“看到结果再决定下一步”是多轮推理：
  streamToolLoop/runToolLoop里的 for i = 0 ; i < AgentToolLoopMax; i++就是干这个的：
  - 模型要工具 -> 你的系统执行 -> 回填 -> 再问一次；
  - 模型不再要工具、给出正文 -> 跳出循环，把正文挡最终回答

#### 4 流式下的tool_calls分片（代码中的toolCallAccumulator的原因）
  流式时模型按token增量输出，tool_calls会被index拆成多片

    // 第 1 片
    {"choices":[{"delta":{"tool_calls":[{"index":0,"id":"call_abc","function":{"name":"get_weather","arguments":"{\"city\":"}}]}}]}
    // 第 2 片
    {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"\"杭州市\""}}]}}]}
    // 第 3 片
    {"choices":[{"delta":{"tool_calls":[{"index":0,"function":{"arguments":"}"}}]}}]}
  所以要按index归并、把arguments拼成完整的JSON --这正是llm_tools.go里toolCallAccumulator(map[int]*ToolCall + strings.Builder)做的。
  它和普通content的流式转发走完全不同的拼接逻辑。

#### 5. 全流式方案

一个必须讲清的约束：必须澄清的协议约束：OpenAI兼容上游（LLM厂家）不支持服务端工具循环 --- 工具结果必须有客户端发起新请求回填。所以“单条上游SSE内跑完工具 -> 结果 -> 再答”在协议上做不到。

因此全流式的正确定义是：把“多次内部上游请求+多次工具执行”编排成一条面向客户端的连续SSE事件流，工具的意图/参数/进度/结果不再静默，最终文本连续衔接---展示与编排层全流式，底层仍是一步一个请求。（“全流式”是展示与编排层连贯，非单链接工具循环）

目前已经实现，即：在chat_controller对应的聊天接口中添加onTool回调函数，在工具调用、工具函数执行过程中等过程中，将状态通过回调函数提示到UI，同时加上心跳机制（3秒）为长工具执行提供状态更新支持。

   - 单次工具调用120s

- 单次LLM调用60s，整体超时

### tool_choice机制

​	对于Agent来讲，工具来源于两部分：一是系统工具（如read,write,edit,grep,glob,bash等），这些工具不需要被设计成独立的skill；二是被定义为skill.md中的tools部分。如果在tool的定义部分加上required属性，这就表示该tool函数必须要被调用，但是对于LLM来讲，这个属性并不是模型能理解的指令，而是推理服务在解码上的约束。模型本身还只是做next-token预测；而这个约束实际上还是由agent来落实的，而落实的方式有两种：

1. 硬约束：受限/引导编码(guided decoding)

   LLM把工具调用定义为一套语法（函数名枚举 + arguments的JSON schema），然后在每一步采用时对logits做掩码；任何会让输出偏离该语法的token概率为-∞。

   - 模型物理上无法吐出普通文本，必然产出tool_calls；
   - vLLM/SGLang的guided_decoding就是这条路，OpenAI也由服务端保证；
   - 极端实现等价于"把<tool_call>/{"name:这一段预算(profile)在assistant轮开头，模型只能从选哪个函数、参数是什么往后续写}"

2. 软约束：提示词/前缀注入

   也就是把工具schema渲染进chat template（Qwen模版是<tool>...</tool>放在system里）+ 追加一句“必须调用一个函数”的文案。这种情况下“保证”来自已经替你写好的前缀或模型的配合，不是100%。指定函数的object形式({"type":"function","function":{"name":"get_weather"}})各家普遍采用前缀注入实现--直接把"name":"get_weather"写死，模型只生成参数

3. 三种取值的实际差异

   | 取值       | 服务端动作                    | 保证                                           |
   | ---------- | ----------------------------- | ---------------------------------------------- |
   | auto       | 不加约束(schema照样给)        | 可能纯文本，也可能调用工具                     |
   | none       | 不给schema或掩掉tool-call语法 | 只可能是文本                                   |
   | required   | 只保留tool-call语法           | 必须调用，但调用哪个由模型选<-这就是所谓的过宽 |
   | object形式 | 语法里固定/预填函数名         | 强制那一个                                     |

   另外，required只保证>=1个调用：模型可以选择一次性发多个tool_calls(parallel_tool_calls允许时)，本系统中累积器按index把他们都收下来(llm_tool_call_accumulator.go的order)，循环里for _, call :range calls 会逐个执行。所以“多个工具都要调”在同一轮中都可能让胜，但这是模型决定的，不是required保证的。

​	thinking模式要求自由生成长链推理文本，而required要求解码空间只能落在工具调用语法里 --- 两者对解码空间的约束是互斥的，所以，dashscope直接拒绝。这也正是关掉思考+required是正确解码的原因。
