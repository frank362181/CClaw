# 简单 / 复杂问题的判定设计（Coordinator 前置决策）

> 状态：设计稿（不落地）
> 上游：[多Agent协作设计方案](./多Agent协作设计方案.md)（已选方案 A：路由内规划）
> 本文只回答一个问题：**一条用户消息，什么时候走现有单 Agent 路由，什么时候升级为 Coordinator 规划。**
> 实现锚点：[agent_router.go:189](../src/cclawservice/harness/ctxmgr/agent_router.go:189) `classifyByLLM`、[context_assembler.go:187](../src/cclawservice/harness/ctxmgr/context_assembler.go:187) `BuildClassifyAgentPrompt`。

---

## 0. 结论先行

**判据不是"问题长短"，而是"一个 Agent 能不能一次做完"。** 把它拆成 4 个可观测维度：

```
D1 能力跨度：需要几个"不同专家"的专业能力？
D2 取证广度：需要几份互不依赖的材料/对象？
D3 依赖深度：是否存在"先算 A 才能算 B"的串行阶段？
D4 交付形态：交付物是否是多段/多表/多节的结构化产物？

复杂 ⇔ D1≥2 或 D2≥3 或 D3≥2 或 (D2≥2 且 D4≥2)
```

判定用**三层管线**，前两层零成本，第三层复用你今天已经有的那次分类调用：

```
L0 硬分流（今天已有，0 成本）  → 直接定案，不进判定
L1 结构信号（纯代码，0 成本）  → 只做"硬提升"：单 Agent 物理上做不到的，直接判复杂
L2 LLM 判定（1 次调用，复用）  → 输出 mode + 置信度 + 证据
L3 运行期/人工升级（v2 可选）  → 简单路径答不好时一次性升级
```

**关键结论：简单问题的成本与延迟完全不变**（仍是"1 次分类 + 1 次回答"），因为 L2 的那次调用本来就要发生——它今天用来选 Agent，现在顺便输出 `mode`。

---

## 1. 为什么必须把"复杂度"操作化

常见但错误的判据：

| 错误判据 | 反例 |
|---|---|
| 字数多 = 复杂 | 贴一篇 3000 字文章要求"总结要点" → 单域、单材料、单阶段，**简单** |
| 字数少 = 简单 | "先查 A、B 两个债务人的诉讼状态，再按回收率排序出表" → 18 个字，**复杂** |
| 有"报告"二字 = 复杂 | "处置报告里诉讼时效怎么算" → 咨询类，**简单** |
| 命中专业词 = 复杂 | "不良资产是什么" → **简单** |

所以复杂度**不是文本属性，而是"任务结构 × 可用能力集合"的属性**：

> 同一个问题，在只有 1 个 Agent 的单位里只能是简单；在有 3 个专业 Agent 的单位里可能是复杂。
> 因此判定必须以**当前候选目录**为条件，不能做成静态词表。

---

## 2. 四个维度的可观测定义

| 维度 | 取值 | 怎么观测（不靠猜） |
|---|---|---|
| **D1 能力跨度** | 需要几个不同 Agent 的专业能力 | 各候选 Agent 的技能 `trigger-keywords` 分别命中 → 命中涉及 **k 个不同 Agent** |
| **D2 取证广度** | 需要几份**互不依赖**的输入 | 消息里出现的文件（`*.pdf/xlsx/docx/md`）、编号/ID、债务人/资产包/项目名的**去重计数**；以及"分别/各自/逐个/每一个"等分配词 |
| **D3 依赖深度** | 串行阶段数 | "先…再…/第一步…第二步/基于…计算/得出…然后/据此"等阶段连接词的数量 |
| **D4 交付形态** | 交付物件数 | 显式要求多种产物（"报告 + 表格""清单 + 结论"），或多级结构要求（"分三部分""每项给出…"） |

四个维度都可以从"文本 + 候选目录"得到，**D1 需要每候选 Agent 的技能关键词集合，但不调用 LLM**（技能元数据已被 `LoadSkills` 按文件指纹缓存）。

## 3. 判定管线

### 3.1 L0：硬分流（0 成本，沿用今天）

这些情况**不进复杂度判定**，因为"选谁"已经被确定性规则定死：

| 顺序 | 条件 | 结果 | 来源标记 |
|---|---|---|---|
| 1 | `routing.complexity.enabled=false` | 简单（今天的行为） | `disabled` |
| 2 | 只有一个可用 Agent | 简单（该 Agent） | `single_agent` |
| 3 | UI 显式指定 `agentId` **且会话非 planner 模式** | 简单（该 Agent） | `explicit` |
| 4 | 会话已绑定 Agent **且会话非 planner 模式** | 简单（绑定值） | `binding` |
| 5 | 关键词规则命中 **且 `keywordRuleMode=direct`** | 简单（规则目标） | `keyword` |

> 第 3、4 条附加的"非 planner 模式"是协作能持续的前提，见 §7。

`keywordRuleMode=hint` 时（建议默认），关键词命中的结果**不短路**，而是作为提示注入 L2。

### 3.2 L1：结构信号（0 成本，硬提升）

定位：**只做加法，不做减法**。它的职责是把"单 Agent 物理上做不到"的问题从模型手里抢回来（提高召回），而不是替模型判断（避免规则误判导致昂贵协作）。

#### 强信号（命中即进入规划路径，不再做"选一个 Agent"的判断）

| 强信号 | 判据 | 为什么不可能误判 |
|---|---|---|
| S1 能力越界 | 技能命中覆盖 **≥2 个不同 Agent** | 一个 Agent 只有自己的技能集，跨了两家就是单 Agent 做不到 |
| S2 材料洪泛 | 去重后的材料计数 **≥3** | 3 份以上互不依赖的长材料，单次上下文无法兼顾（且必然需要分段取证） |

```go
// 表达能力可比性:D1 用"实际命中"而不是"目录里能不能"
func strongSignals(msg string, catalog []AgentSkills) bool {
    hits := map[string]int{}
    for _, a := range catalog {
        if n := countSkillKeywordHits(msg, a); n > 0 {
            hits[a.AgentID] = n
        }
    }
    if len(hits) >= 2 { return true }              // S1
    if distinctMaterials(msg) >= 3 { return true } // S2
    return false
}
```

强信号的执行方式与兜底：命中后**用规划提示词**（并在 prompt 里显式声明"本次必须 delegate"）发起调用，因此模型不会退回"选一个 Agent 就完事"。若模型仍返回 `mode=single`，则以模型的 Agent 选择为准，并记录 `deviation=strong_signal_single` 供分析——**不强行拼凑计划**，因为规则仍可能误判（例如材料标题里出现了三个文件名，但只需要读其中一个）。

#### 弱信号（只作为证据交给模型，不单独提升）

| 弱信号 | 判据 |
|---|---|
| W1 多诉求 | 问句 ≥2，或出现枚举结构（`1.`/`①`/`第一`/换行分条） |
| W2 对比并列 | `对比/比较/分别/各自/异同/优劣/区别` + 出现 ≥2 个实体 |
| W3 多材料 | 去重材料计数 = 2 |
| W4 串行阶段 | 阶段连接词 ≥1 |
| W5 多交付物 | 显式要求 ≥2 种产物形态 |
| W6 篇幅（**仅提示**） | > 1500 字 —— **单独出现一律不提升**，只作为 prompt 里的一条说明 |

弱信号统计口径：`weakCount = W1..W5 中为真的个数`。`weakCount ≥ 2` 时在 prompt 中标注"倾向复杂"，否则标注"倾向简单"，二者都不强制。

### 3.3 L2：LLM 判定（1 次调用，复用现有分类调用位）

**这是本方案能落地的关键**：今天 [classifyByLLM](../src/cclawservice/harness/ctxmgr/agent_router.go:189) 已经有一次 `SimpleComplete`，把它的输出协议从"一个 AgentId"升级为"mode + 证据"，调用次数不变。

#### 输出协议（严格 JSON，单次）

```json
{
  "mode": "single",
  "agent": "agent_001",
  "intent": "咨询处置报告中的诉讼时效计算口径",
  "signals": {"capability_span": 1, "evidence_breadth": 0, "dependency_depth": 0, "deliverable": 1},
  "confidence": 0.92
}
```

```json
{
  "mode": "delegate",
  "intent": "对比 A、B 两个资产包的处置价值并出对比报告",
  "signals": {"capability_span": 2, "evidence_breadth": 2, "dependency_depth": 2, "deliverable": 2},
  "confidence": 0.81,
  "tasks": [
    {"id":"t1","agent":"agent_001","action":"提取 A 包 2024 年资产负债与利润表主要科目，输出 markdown 表（单位万元）","depends_on":[],"priority":10},
    {"id":"t2","agent":"agent_001","action":"提取 B 包 2024 年资产负债与利润表主要科目，输出 markdown 表（单位万元）","depends_on":[],"priority":10},
    {"id":"t3","agent":"agent_002","action":"基于 t1、t2 的科目表计算资产负债率/有息负债率/净利率，列出差异超 20% 的科目","depends_on":["t1","t2"],"priority":10}
  ],
  "reporter": "agent_002"
}
```

设计要点：

1. **先证据后结论**：要求模型先填 `signals` 四个计数，再给 `mode`。同一模型下，这种"强制先量化再判断"的输出比直接问"简单还是复杂"稳定得多（也顺带让决策可解释、可统计）。
2. **`signals` 与 `mode` 必须自洽**：程序校验 `mode==delegate` 时至少要有一维 ≥2（按 §0 的判据）；不自洽则以 `signals` 重算 `mode`。
3. **`confidence`** 只用于 `delegate` 的准入门槛（见 §3.4）。
4. **`intent`** 必填，用于 UI 展示"我理解你要什么"和日志归因。

#### 提示词骨架

```markdown
你是任务分诊器。先判断一个问题需要"一个专家"还是"多个专家协作"，再做相应的输出。

# 复杂度判据（必须逐项量化，不要凭感觉）
D1 能力跨度：需要几个不同专家的专业能力？（看候选目录里的领域标签）
D2 取证广度：需要几份互不依赖的材料/对象？（文件、编号、债务人、资产包各自算一份）
D3 依赖深度：有几段串行阶段？（需要先得到结果才能算下一步的，算一段）
D4 交付形态：交付物有几种？（只要一段结论=1，多表/多节/多种产物≥2）

判定：D1≥2 或 D2≥3 或 D3≥2 或 (D2≥2 且 D4≥2) → delegate；否则 single。

# 反例（这些都不要判成复杂）
- 贴一篇长文要求"总结要点"：D1=1,D2=1,D3=0 → single
- "处置报告里诉讼时效怎么算"：咨询类 → single
- 只是要求"写详细一点/多举例子"：输出长度不是 D4

# 候选专家（编号|名称|领域标签）
- agent_001|不良资产智能助手|尽调/估值/处置/债权/抵押物
- agent_002|通用助手|报表分析/比率计算/通用问答

# 输出（严格 JSON，无解释、无代码块标记）
```

#### 三级退化（不倒退保证）

```
① JSON 解析成功 + 校验通过          → 使用
② JSON 失败 → 整段文本精确等于某个 AgentId → single（= 今天的行为）
③ 仍失败/超时/空                    → defaultAgent 单跑（= 今天的兜底）
```

配一个额外保险：`mode=delegate` 但有效任务 <2 → 自动降为 `single`（用第一个有效任务的 Agent，或模型给的 `agent`）。理由：单任务计划只会白花一次汇总调用。

### 3.4 置信度门槛（只卡 delegate）

```go
if mode == delegate && confidence < cfg.DelegateConfidence { mode = single }
```

默认 `DelegateConfidence = 0.6`。理由是不对称代价：

- **假复杂**（simple 判成 complex）：多花 N 次 Worker + 1 次汇总，延迟从 ~3s 涨到 ~20s，成本翻几倍，且**用户能感知**；
- **假简单**（complex 判成 simple）：只用一个专家答，答案看起来完整但片面，**用户感知不到**。

两者都不可接受，但前者有明确的上界（超时可以熔断），后者会持续污染可信度。所以：

- 用**强信号**兜住最严重的假简单（S1/S2 是"物理做不到"，不是概率问题）；
- 用**置信度门槛**兜住假复杂；
- 剩下的灰区交给人工覆盖（§8）。

### 3.5 L3：运行期升级 / 人工覆盖（v2，可选）

| 方式 | 触发 | 成本 |
|---|---|---|
| 人工强制协作 | UI 上"深度分析"开关 → `forceMode=delegate` | 0 额外判定 |
| 人工强制快速 | UI 上"快速回答"→ `forceMode=single` | 0 |
| 结果不满意后重答 | 消息气泡上的"用协作重答" | 1 次规划 + N |
| 运行期自升级 | 单 Agent 回答自评"信息不足/需要其他专业"（需新增一次轻量自评） | +1 次调用 |

v1 只做前三条（都是显式、零风险）；第 4 条先不做（会让简单路径也可能变成 2 次调用）。

## 5. 与现有代码的接缝

### 5.1 `Resolve` 的返回类型要升级

今天返回 `dataobject.TAgent`，只够表达"用谁"。需要扩成：

```go
// harness/ctxmgr/route_decision.go
type RouteMode int
const (
    RouteModeSingle   RouteMode = iota // 今天的行为
    RouteModeDelegate                   // 走规划
)

type RouteSource int
const (
    SourceDisabled RouteSource = iota
    SourceForced
    SourceSessionPlanner
    SourceExplicit
    SourceBinding
    SourceSingleAgent
    SourceKeyword
    SourceStructStrong
    SourceLLM
    SourceFallback
)

type RouteDecision struct {
    Mode     RouteMode
    Agent    dataobject.TAgent   // Mode=single 时的目标
    Plan     *ExecutionPlan      // Mode=delegate 时的计划（含 Reporter）
    Source   RouteSource
    Intent   string
    Signals  ComplexitySignals   // 四维计数（可观测 + 复算 mode）
    Confidence float64
    ElapseMs int64
    Note     string              // 降级/偏离原因
}
```

`Resolve` 保留为薄包装（`return decision.Agent`），调用点与测试不受影响；新增 `ResolveDecision` 供 `Preparer` 使用。

### 5.2 判定输入

```go
type DecisionInput struct {
    ComCode, SessionID, Message string
    ExplicitAgentID             string
    Agents                      []dataobject.TAgent // 已过滤（未删除/未禁用）
    Catalog                     []AgentSkills       // agent → 技能触发词（用于 D1）
    KeywordHint                 *dataobject.TAgent  // keywordRuleMode=hint 时
    RecentSummary               string              // planner 会话的上一轮摘要（可选）
    ForceMode                   RouteMode
    ForceSet                    bool
}
```

`Catalog` 的来源：`agentRepo.GetSkillsByAgent(agent)` + `AgentDocCache.LoadSkills`（已按文件指纹缓存）。**冷启动后每次判定只是内存查表**。

### 5.3 结构化信号检测器（纯函数，可单测）

```go
// harness/ctxmgr/complexity.go
type ComplexitySignals struct {
    CapabilitySpan, EvidenceBreadth, DependencyDepth, Deliverable int
    Materials      []string // 去重后的材料标识（日志/调试用）
    HitAgents      []string
    WeakHits       []string // "W1","W2"…
    StrongReason   string   // "S1"/"S2"/空
}

func DetectSignals(msg string, catalog []AgentSkills) ComplexitySignals
```

纯函数、无 IO、无 LLM ⇒ 可以拿一份真实的 100 条问题集做离线回归，阈值调整有据可依。

## 6. 成本与延迟模型

| 分支 | 今天 | 方案 A 后 | 差异 |
|---|---|---|---|
| 显式 / 绑定 / 关键词 / 唯一 Agent | 0 + 1 = **1 次** | 同 | **无** |
| 简单问题（L2 判 single） | 1（分类）+1（回答）= **2 次** | 1（分诊）+1（回答）= **2 次** | **无** |
| 复杂问题（L2 判 delegate） | 1+1 = 2 次，但答案片面 | 1（分诊，产出计划）+N（Worker）+1（汇总） | +N+1 次，延迟 ×3~10 |
| L1 强信号 | 1+1 | 1（规划）+N+1 | 同上（省掉"分类"那一步，因为直接规划） |

一句话：**只有真正需要协作的轮次才变贵，其余一分钱不多花。**

## 7. 多轮会话：绑定短路会杀死协作

今天的第 ③ 段（会话绑定）会让**同一会话的第 2..n 轮永远不再路由**。这对单 Agent 是对的（保证上下文一致），但对协作是致命的：

```
用户：把 A、B 两个包的数据拉出来做对比   → 首轮判 complex → 协作 ✓
用户：再把 C 包也加进来一起比              → 会话已绑定 agent_002 → 单 Agent ✗（无 B 包上下文执行者）
```

另外，最新代码里 UI 会把 `t_session.agent_id` 回传成显式 `agentId`，这会让第 3 条 L0 也短路。

### 7.1 解法：会话级 `routing_mode`

`t_session` 增加一列（或复用 `end_reason` 之外的保留位，建议新增明确列）：

```sql
ALTER TABLE t_session ADD COLUMN routing_mode INTEGER NOT NULL DEFAULT 0; -- 0 绑定Agent / 1 规划器
```

| 首轮判定 | 落库 | 后续轮次 |
|---|---|---|
| single | `routing_mode=0`, `agent_id=<选中>` | 沿用今天的绑定语义（**完全不变**） |
| delegate | `routing_mode=1`, `agent_id=<Reporter>` | **每轮重新分诊**（跳过第 3/4/5 条 L0），规划时带上上一轮摘要 |

这样做的好处：

- 普通会话的行为**一个字都没变**；
- 协作会话"入口是规划器"，语义自洽；
- UI 的 Agent 徽标仍有确定值（Reporter），不会出现"空 Agent"；
- 因为 planner 会话每轮都要读 DB 才能知道模式，建议复用现有内存注册表缓存：`ChatSessionAgentRegistry` 的条目从 `{agentId, boundAt}` 扩展为 `{agentId, routingMode, boundAt}`，DB 只在缓存未命中时读一次。

### 7.2 规划时的上下文

planner 会话的第 n 轮，规划输入 = **本轮消息 + 上一轮摘要**（不是全文）。这样"再把 C 包加进来"这类追问能被正确理解为"补 t2.5"。

## 8. 误判的处理

| 情形 | 用户感受 | 缓解 |
|---|---|---|
| 假复杂 | 变慢、变贵 | `confidence` 门槛；`maxTasks`；`tasks<2 ⇒ single`；单轮总超时熔断（`AgentRunTimeout`） |
| 假简单 | 答案片面但看起来完整 | L1 强信号兜底；`keywordRuleMode=hint` 让关键词也参与；UI 提供"用协作重答" |
| 模型反复无常 | 同类问题时simple时complex | `temperature` 设 0；prompt 固定 few-shot；记录决策 → 离线统计同类问题的一致性 |
| 一个单位只有一个专家 | 永远不会协作 | 正确行为：D1 恒为 1。协作能力随 Agent 数量自然生效 |

## 9. 可观测、灰度、评测

### 9.1 决策留痕

```sql
CREATE TABLE IF NOT EXISTS t_route_decision (
    ID          INTEGER PRIMARY KEY AUTOINCREMENT,
    turn_id     VARCHAR(40) NOT NULL UNIQUE,
    session_id  VARCHAR(40) NOT NULL,
    mode        INTEGER NOT NULL,          -- 0 simple / 1 delegate
    source      INTEGER NOT NULL,          -- 见 RouteSource
    agent_id    VARCHAR(8),
    intent       VARCHAR(512),
    signals     VARCHAR(64),               -- "2,2,2,2"
    confidence  REAL,
    elapse_ms   INTEGER,
    note        VARCHAR(256),
    created_at  INTEGER NOT NULL
);
```

有了它，"为什么这条问题没走协作"永远可以事后回答，不用猜。

### 9.2 灰度：先只决策、不执行

**这是最推荐的落地第一刀**：

```
cfg.CoordinatorDryRun = true
  → 照常判定、照常落 t_route_decision
  → 但执行永远走单 Agent（今天的路径）
```

跑 1~2 周真实流量后，你会得到：计划率分布、按 source 的分布、平均信号强度。**零风险拿到数据**，再决定门槛。

### 9.3 指标

| 指标 | 目标 |
|---|---|
| 计划率（delegate 占比） | 5%~20%（超出说明判据过松；为 0 说明没生效） |
| 假复杂率（人工抽检计划中"本可一次答完"的比例） | < 15% |
| 简单路径 P95 延迟 | 与今天持平（±5%） |
| 协作轮成功率（含部分产出的比例） | > 95% |
| 同类问题判定一致性（相同问题跑 3 次） | > 90% |

### 9.4 离线评测集

先攒 150~200 条真实问题，人工标注 simple/complex，做成回归集：

```
precision(delegate) = 判复杂中真的复杂的比例   ← 控制成本
recall(delegate)    = 真复杂中被判出来的比例   ← 控制质量
```

阈值调整只允许"用这个集子跑完再改"，不允许拍脑袋。

## 14. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 判据本身是主观的 | 不同人对"复杂"定义不同 | 用 4 维可量化定义 + 评测集锁定口径 |
| 依赖候选目录 | 同一问题在不同单位结论不同 | 这是**正确**行为（能力集合不同），不当作缺陷 |
| 模型偏保守/偏激进 | 永远答 single 或永远答 delegate | `signals` 自洽校验 + 置信度门槛 + 一致性抽检 |
| 强信号误判 | 技能关键词命中但问题其实简单 | 强信号只在"覆盖 ≥2 个**不同** Agent"时生效；命中单 Agent 不算 |
| 关键词 hint 噪声 | `keywordRuleMode=hint` 把关键词塞给模型 | hint 只作为弱证据，不提升等级 |
| 多轮退化 | 绑定短路使协作只在首轮 | `routing_mode=planner` + 每轮重新分诊（§7） |
| 决策不可解释 | 用户不知道为什么变慢 | `intent` + `t_route_decision` + UI 展示计划卡片 |

## 15. 待确认

1. **`keywordRuleMode` 默认 `hint` 还是 `direct`**？`direct` 完全保持今天行为，但含关键词的跨领域问题永远进不了协作。
2. **`t_session.routing_mode` 是否接受**？这是本方案唯一需要"改会话语义"的地方（也只影响被判为复杂的会话）。
3. **`qualityPreset` 默认 `balanced`** 是否合适？
4. **是否需要"每次都用协作"的单位级开关**（某些单位宁可慢也要全）？
5. **评测集由谁标注**？建议先用 dryRun 数据挑 200 条，业务同事标一次，之后季度复标。
