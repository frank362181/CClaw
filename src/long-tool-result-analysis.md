# 长工具结果"尾部信息丢失"：三个方案的取舍

| 项 | 内容 |
|---|---|
| 问题 | 工具结果超过阈值后，**尾部**信息从"下一轮"起就再也进不了任何模型调用（不复述、不进摘要、不进长期记忆） |
| 事实 | 现网最长 tool 记录 **8289 字符**（`read`）；`npa_ingest` 整目录结果实测 **44,902 字符** |
| 结论 | 三个方案**各救一段**：A 只放宽阈值、B 换掉载体（收益最大）、C 才真正解决"尾部进摘要"，但 C 最贵且收益最不确定。**建议 A + B 组合，C 只在确认"要害信息无法结构化"时再做** |

---

## 一、先把"信息在哪一步丢的"说清（决定每个方案能救什么）

| 闸门 | 当前值 | 代码位置 | 限制的是 | 谁能救尾部 |
|---|---|---|---|---|
| 脚本输出硬限 | **256 KB** / stdout、stderr 各 | `execbox/script_runner.go:34` | 源头体量 | —（与记忆无关） |
| 历史文件 | **无截断** | `memory_service.go:767` | 唯一完整副本 | —（改动它会失去可重放性） |
| 回放上限 | **1200 rune** | `context_assembler.go:1003` + `DefaultToolReplayMaxRunes` | 模型**每轮**看到的 | A / B / D |
| 摘录上限 | **2000 rune** | `compaction.go:343` + `MemoryExcerptRunes` | 摘要/蒸馏模型的输入 | A（同源时）/ B / C |
| DB 摘要列 | 256 rune（无省略号） | `memory_service.go:763` | 只是 DB 列 | — |

**补充事实（重要）**：`ContextPolicy.ToolReplayMaxRunes` **今天没有任何配置入口** —— 全仓只有"结构体字段 + 归一默认（`harness_member.go:142`）+ 装配读取"三处，没有任何地方给它赋值。也就是说：**回放上限恒为 1200，改不了**。方案 A 实际上是在补第一个配置面。

可见性衰减（同一条记录的一生）：

```
同一轮内   完整结果（BuildToolResultMessage，不截断）      ← 模型唯一一次看到全文
下一轮起   前 1200 rune + "…"（回放）
进摘要时   前 2000 rune + "…"（压缩/蒸馏输入）
第 2000+   只存在于磁盘：不回放、不进摘要、不进 MEMORY.md   ← 永久沉默
```

## 二、方案 A：按工具声明 `max_history_runes`

**落点（三处，都不碰存储格式与摘要契约）**
1. 声明通道：`BasicTool`（`harness_tool.go:54`，技能工具来自 SKILL.md `tools:`）+ `SystemToolSchemaMeta`（`:64`，系统工具来自 `read.json` 等）各加一个字段 —— 2 个结构、2 个解析入口。必须走"工具 schema 单一来源"，不能另开一份配置表（否则又会出现"目录与实际下发不一致"的老毛病）。
2. 传递：`tool_repository` 把声明带进 dispatch bundle → `ContextPolicy` 加 `ToolRunesCaps map[string]int`，由 `prepareChat` 填充（可按 agentId 缓存，与 `toolsReserveTokens` 同一模式）。
3. 生效：`renderToolBlock`（回放）与 `compactionPromptLine`（摘录）**共用同一个查找函数**，一处声明两处生效。

**取舍**

| | |
|---|---|
| ✅ | 声明式、可审计、可精准（`npa_ingest: 8000`、`get_weather: 400`）；顺带补上"回放上限不可配"这个缺口 |
| ✅ | 改动面最小：不碰 `covers` 契约、不碰历史文件格式、不碰压缩编排 |
| ❌ | **只放宽阈值，不解决"阈值之上仍然丢"**：20000 rune 的结果给到 8000，仍丢 12000 |
| ❌ | 静态阈值 vs 动态产出：同一个 `npa_ingest` 小目录产出 2K、大目录产出 44K，一个数字服务不了两种场景 |
| ❌ | 与历史预算是**零和**：调大回放 → 更早触发压缩 → 压缩又要调用 LLM（把成本从"信息丢失"换成"更频繁压缩"，未必更省） |
| ❌ | 三处上限仍未同源：A 若只改回放、不改摘录，就复现今天的"1200 vs 2000"式错配 |

**适合**：输出"天然短、偶尔长"的工具（weather/read 类），以及作为所有方案的兜底旋钮。**不适合**作为"大工具"的主力方案。

## 三、方案 B：结构化落盘（pointer / 回执模式）

**今天的现状已经有一半**：`npa_ingest` 声明里就有 `emit_stdout`、`max_pages_per_file`、`max_chars_per_page`、`max_chars_per_file`、`context_style`、`ocr` 等参数，SKILL.md 也明确写了"整目录 ingest ≈ 1 轮 + 数十秒 + 大上下文，能省则省 —— 大目录请 `emit_stdout:false` 只回执落盘与概要"。**那 44,902 字符的记录来自一次没加该参数的调用** —— 即"能力已有，纪律没有"。

**三种落地形态**
| 形态 | 做法 | 硬度 |
|---|---|---|
| B1 提示词/SOP 纪律 | 靠 SKILL.md 教模型传 `emit_stdout:false` | 最软：忘了就白搭（今天的情形） |
| B2 工具声明 `history_mode: pointer` | 记忆层按声明只存"回执 + 概要" | 中：要靠 A 的声明通道 |
| B3 记忆层识别回执 | 结果 JSON 里含 `result_file.path`/`manifest_file` → 自动只留回执 + 概要 | 最硬：不依赖模型自觉，但属于"猜结构" |

**取舍**

| | |
|---|---|
| ✅ | 收益最大且**一次解决三处压力**：44K → ~500 字符（回放、摘录、磁盘、token 全降一个数量级） |
| ✅ | 语义由工具自己负责（历史里留的就是工具给的摘要），记忆层不需要理解业务 |
| ❌ | **指针会烂**：产物在 `<exeDir>/temp/runs/<run_id>/`，而保留策略是 `keep_runs=20`（实测当前正好 20 个目录，pruning 已在生效）⇒ 历史里的 `result_file.path` 会指向**已被删除**的 run；审计、重放、重新蒸馏全部断链 |
| ❌ | **可重放性下降**：压缩/蒸馏以后只能读到回执，无法回读全文（除非产物还在且格式稳定）—— 与"历史文件是唯一完整副本"的隐含承诺冲突 |
| ❌ | 备份/迁移要"连产物一起搬"：今天产物（temp）与历史（cclaw/chat_history）是同一 exeDir 下的两个目录，没有"会话包"概念 |
| ❌ | B3 的"识别回执"依赖结果结构约定，工具换一种返回形态就失效（需要把约定写进工具契约并加校验） |

**前置条件（不做这两件，B 会留下断链债务）**
1. 产物目录从 `temp/runs` 改为**会话级持久目录**（如 `cclaw/chat_history/<owner>/<sessionId>/artifacts/`），生命周期与会话一致，清理策略从"按轮数"改为"按会话/配额"；
2. 明确"历史文件 + 产物"是一个整体（备份/迁移/合规删除的边界）。

**适合**：输出天然大、且本来就落盘的工具（ingest/extract/report、任何 OCR/文件解析类）。**这是这类工具的终局方案。**

## 四、方案 C：分片摘要

**现状：分块机制只到"区间级"，没有"单条内部分块"**。已有的分块是 `compaction.go:319-330`（mode=1 safeguard 按**记录区间**分块多次调用再拼接）；`compactionPromptLine` 对**单条**记录是硬截断。

**根本障碍（比成本更麻烦）**：摘要的覆盖契约是**记录序号闭区间** `covers: from-to`（`buildSummaryRecordContent`、读取端 `ActivePlainRecords`/`verifyCovers`/取代判定全建立在它上面）。"覆盖 47 号记录的**后半段**"这句话**表达不出来**。

**三条实现路径**

| 路径 | 做法 | 契约影响 | 成本 |
|---|---|---|---|
| C1 子记录 | 长记录落盘时拆成 `[47.1] [47.2] …` | 序号分配 + "同轮工具折叠成一条 assistant 消息"的逻辑都要改（`buildHistoryItems` 按 user 分组折叠） | 中高 |
| C2 记录级 digest | 超长记录先单独生成一条 `summary`（`covers: 47-47`），其正文由分片调用拼出；只对超长记录做 | 契约**不破**（单条覆盖） | 中（但要与"压缩不得越过水位"的钳制协同，避免打架） |
| C3 直接放宽上限 | 把 `MemoryExcerptRunes` 调到能装下最长记录 | 无 | 低，但会顶爆 `MaxCompactionInputChars=24000` → 触发区间收缩 → 压不动并反复重试（现有 fail 路径） |

**取舍**

| | |
|---|---|
| ✅ | **唯一**能真正做到"尾部信息进摘要/长期记忆"的方案 |
| ❌ | 成本随长度线性增长：200KB 结果按 2000/片 = **100 次 LLM 调用**（必须限制分片数，否则成本与延迟都不可接受） |
| ❌ | 复杂度最高：C1 碰序号契约，C2 碰压缩编排与水位防吞，两者都属于"整套设计里最贵的改动面" |
| ❌ | **收益不确定**：长工具结果里真正该长期记住的，往往是结构化字段（JSON 尾部的 `summary`/`materials_check`）—— 那正是 B 要承载的东西；用 C 去救它，等于用最贵的手段解决已经被 B 覆盖的问题 |

**适合**：极少数"长、且尾部含关键信息、又无法结构化"的工具（超长日志/文档扫描结果）。**不适合作为通用机制**。

## 五、方案 D（补充，成本最低）：源头治理

- **今天就能用**：工具的既有参数（`emit_stdout:false`、`max_chars_per_file`、`max_pages_per_file`、`context_style:"text"`）+ SOP 纪律，能把 44K 压到几百字符，零代码改动。
- **记忆层可加的最小硬约束**：写入时按声明截断（把"回放上限"的语义前移到写入侧，历史里存"截断 + 指针"）—— 磁盘体积随之下降，但**牺牲"唯一完整副本"**，建议只对声明了 pointer 语义的工具启用。
- 取舍：✅ 立即生效、零契约改动；❌ 靠模型自觉、没有兜底（模型不加参数时照样写 44K）。

## 六、组合建议（判定树）

```
工具输出体量天然可控（< 2K rune）
    → 不管（现状够用）

输出偶尔长、且无落盘产物（read/grep 类）
    → 方案 A：声明 max_history_runes（回放与摘录同源）+ 方案 D 的 SOP 纪律

输出天然大、且本来就落盘（ingest/extract/OCR 类）
    → 方案 B（B2 声明 + B3 兜底），前置条件：产物改会话级持久目录
      ⇒ 这是收益/成本比最高的一档：一个数量级，且一次解决三处压力

输出大、不落盘、且确认尾部含要害信息
    → 方案 C2（记录级 digest，限制分片数），最后才做
      ⇒ 若能在工具侧把这部分信息摘要出来，仍应回到 B
```

**推进顺序建议**：先做 **B 的前置条件（产物持久化）** → 再做 **A（声明通道 + 回放/摘录同源）** → 最后按需评估 **C2**。
理由：A 是 B 的声明通道（复用同一字段与传递链路），先做 A 后做 B 可以少改一次；而 C 的成本是前两者的数倍，且收益被 B 大部分覆盖。

## 七、需要你决策的三个问题

1. **历史文件是否继续承担"唯一完整副本"的角色？**
   （是 ⇒ 方案 B 必须做成"回执 + 产物"整体语义；否 ⇒ A/D 的"写入侧截断"才有空间）
2. **`bin/temp/runs` 的 `keep_runs=20` 是否改为"会话级持久 + 显式清理"？**
   （B 的前提；不改就是"历史里的指针会烂"）
3. **长工具结果的"要害信息"能否由工具自己摘要出来？**
   （能 ⇒ 走 B；不能 ⇒ 才值得投入 C2）

## 八、只读量化（2026-09-30，未改任何代码）

**方法**：把"工具结果"按两种回执口径重算体积（只读现网文件）：
- **R1 标准回执**：递归把大数组替换为 `{"count": n, "sample": [首元素]}`（首元素内长字符串截到 120），保留标量与小结；
- **R2 最小回执**：只保留白名单键（`ok/error/run_id/result_file/manifest_file/input/summary/materials_check/warnings`）。
- 同时输出**不设上限**的自然体量，避免"省下的量"是被我设的上限造出来的。

### 样本 S1：现网历史文件里的 tool 记录 → **收益 0%**

现网只有 **1 个**历史文件（`chat_history/d/memory_100001f5cc…md`，26.7KB，53 条记录，其中 tool 记录 **7 条**）：

| idx | 工具 | 全文(rune) | 是 JSON | 回执适用 | 摘录口径(2000) |
|---|---|---|---|---|---|
| 47 | `read` | **8284** | ❌ 纯文本 | **不适用**（无落盘产物） | 截断，尾部丢 **6284** |
| 44/39/32/17/6/52 | `get_weather` | 60–76 | ❌ | 不需要 | 完整 |

⇒ **现网历史文件里，方案 B 一条覆盖不到**（B 只对"本来就落盘"的工具生效）。这 7 条里唯一的大记录是 `read`，它的解法是**方案 A（声明 `max_history_runes`）**，不是 B。

### 样本 S2：现网工具产物（= 同批工具跑"全文模式"会写进历史的内容） → **省 95%~99%**

95 个样本（`bin/temp/runs/*/parsed_context.json`、`manifest.json`、`bin/temp/legacy/parsed_context_*.json`、`extracted_metrics_*.json`，全部是真实运行产物）：

| 样本 | 全文(rune) | R1 回执 | R2 回执 | 全文模式下尾部永久丢 |
|---|---|---|---|---|
| `legacy/parsed_context_2026_09_18.json` | 124,838 | 800 | **149** | 122,838 |
| `legacy/parsed_context_2026_09_15.json` | 117,744 | 800 | 149 | 115,744 |
| `runs/20260921_223839/parsed_context.json` | 102,714 | 800 | 179 | 100,714 |
| `legacy/extracted_metrics_2026_09_18.json` | 27,476 | 800 | 267 | 25,476 |
| `runs/20260921_223839/manifest.json` | 11,535 | 760 | 163 | 9,535 |
| …（95 个） | | | | |
| **合计** | **1,440,231** | **74,004 (省 95%)** | **15,299 (省 99%)** | **1,271,471 → 0** |

**不设上限**的自然回执体量：R1 93,832（省 93.5%）/ R2 15,299（省 98.9%）
⇒ 省下来的量**不是上限造出来的**（R2 完全无上限也只占 1.1%）。按项目内的换算（1.5 rune/token，CJK 保守口径）：**10,107 token/条 → 519 token/条**。

### 三个实际口径的对照（按 S2 均值 15,160 rune/条）

| 口径 | 全文模式 | 回执模式 | 变化 |
|---|---|---|---|
| 历史文件磁盘体积 | 1,440,231 | 74,004 | **−95%** |
| **回放注入 prompt / 条**（cap 1200） | 1200（**被截断**） | **779（完整）** | 体积仅 −35% |
| **摘录注入摘要 / 条**（cap 2000） | 2000（**被截断**） | **779（完整）** | 体积 −61%，且**尾部不再丢** |
| 一次压缩能装下的记录数（预算 24,000） | **1.6 条** | **30.8 条** | **19 倍** |

### 结论（与直觉不同的三点）

1. **B 不是"省 prompt token"的方案，而是"让信息完整可见"的方案。** 回放本来就有 1200 硬截断，所以 B 对"每轮注入量"只降 35%；真正的收益在**摘录口径（尾部不再永久丢失）**和**压缩预算（1.6 → 30.8 条）**。
2. **B 的收益完全取决于"有没有大工具真的在跑全文模式"**：现网历史文件里 **0 条适用**（只有天气与一次 `read`），而现网产物目录里躺着 **95 个适用样本、144 万 rune** —— 说明这类工具**确实产出过大结果**，只是没有落进这份历史。所以 B 的收益在上线后才会显现，且**必须配合硬约束**（B2/B3），否则模型不加 `emit_stdout:false` 就白搭。
3. **`read` 这类"纯文本、无产物"的长结果 B 覆盖不到** —— 它的唯一解法是 A（声明 `max_history_runes`）或 D（源头约束）。S1 里那 8284 rune 的 `read` 有 6284 rune 的尾部永久丢失，正是 A 的目标场景。

### 对推进顺序的修正

原建议"先做 B 的前置条件"现在要加一条：**A 的优先级与 B 并列** ——
- 现网 7 条 tool 记录里，**B 命中 0 条、A 命中 1 条**（唯一的大记录）；
- B 的收益要等"大工具 + 硬约束"同时到位才释放，而 A 是**当天就能覆盖现有形态**的兜底；
- 且 A 的声明通道正是 B2 需要的通道，先做 A 可以少改一次。
