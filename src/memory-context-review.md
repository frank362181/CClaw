# 记忆与上下文管理：五个角度的分析与方案

| 项 | 内容 |
|---|---|
| 范围 | `harness/mstorage`（记忆读/写/压缩/蒸馏）+ `harness/ctxmgr`（装配/system prompt）+ `service/chat_service`（编排） |
| 方式 | 只读代码 + 现有库/文件事实；**本文件只做分析与方案，不改代码** |
| 结论摘要 | 最严重的三处：**① 隔离维度不统一**（会话按租户、历史目录按登录名）②**群聊语义整体缺失**（多发言人写不进、读不出）③**缓存顺序错误**（每轮变的"当前时间"排在低频变的"历史摘要"之前） |

## 角度一：多租户下聊天历史如何隔离

### 现状（代码事实）

| 资产 | 隔离维度 | 分租户? | 证据 |
|---|---|---|---|
| `session_id` | `comCode` 前缀 | ✅ | `chat_service.go:377-393` `NormalizeCompactId(comCode + clientSessionId)` |
| `t_session` / `t_turn` / `t_turn_tool` | 靠 `session_id` | ✅ | `data/ddl_sqlite3.sql`（表内**没有**租户列） |
| 历史文件**文件名** | `session_id`（含前缀） | ✅ | `harness_utility.go:322` |
| 历史文件**目录** | `sender`（登录名） | ❌ | `harness_utility.go:309` `BuildMemoryRoot(sender)` |
| 归属判定 | `sender` 单键 | ❌ | `memory_service.go:154` `EqualFold(sender, existing.Sender)` |
| 中断键 | `sender:turnId` | ❌ | `harness_utility.go:365` |
| 技能/启动文档工作区 | `owner_id`(=comCode) + agentDir | ✅ | `t_agent.owner_id` |
| 长期记忆 `MEMORY.md` | `owner_id` + agentDir | ✅ | `cCommon.MemoryDocPath` |
| 会话↔Agent 绑定(Redis) | `session_id` | ✅ | `ctxmgr/session_agent_mgr.go`（键就是 sessionId，见 `prepareChat` 第 3 步先加前缀） |

**关键事实**：`t_account` 的主键是 `PRIMARY KEY ("login_name")`（**全局唯一**），同时又有 `com_code` 列（现有两行：`d@100001`、`c@100002`）。也就是说 —— **今天"同名不同租户"根本不可能出现**，历史目录冲突是被这个"与多租户语义自相矛盾的主键"偶然挡住的。

### 问题

1. **两套隔离维度不统一**：会话链路按租户（comCode 前缀），历史目录链路按登录名，长期记忆链路按 ownerId。同一份"归属"在三条链路上用了三个不同的键。
2. 一旦支持"每个单位各自开账号"（`t_account.com_code` 的存在说明这正是产品意图），立刻出现四个破口：
   - `chat_history/d/` 被两个租户混用（同目录混放，运维无法按租户备份/配额/清理）；
   - **归属守卫失效**：B 租户的 `d` 只要拿到 A 租户的 `sessionId` 就能读/写其会话与历史文件 —— 而 `sessionId` 的前缀就是 comCode（低熵、非密钥，且客户端本来就持有 sessionId）；
   - `ForgetSession` 按**目录前缀**丢缓存 → 误清另一租户（`memory_file_storage.go` 缓存键是文件绝对路径，前缀含 sender）；
   - 中断键 `sender:turnId` 跨租户可命中（turnId 是客户端生成的低熵 uuid）。
3. `MemoryService.Begin(sender, agent, req)` **签名里没有租户** → 归属判定的输入天生不完整，改造要同时动 `mstorage`（签名/守卫）、`harness_utility`（目录/文件名）、`service`（调用点/中断键）。
4. **没有租户级的删除/导出/合规入口**：历史散落在 `chat_history/<sender>/*.md`，租户级清理只能 `rm -rf`，且没有 API 能列出/导出（controller 里没有任何会话/历史读取接口）。
5. **用户标识直接当路径段**：`sender` 未做路径安全校验就参与 `ResolvePath`（`NormalizePath` 不清理 `..`），注册/改名策略一变就有越界风险。

### 方案

**方案 A（推荐）：统一 ownerKey + 租户分层目录**
- 引入 `OwnerKey{comCode, sender}`，所有 sender 相关处一律用它：历史目录、`Begin` 守卫、中断键、缓存键、`t_session.sender` 判定。
- 目录改为 `chat_history/<comCode>/<sender>/memory_<sessionId><ts>.md`（按租户分层：便于配额/备份/清理/合规，也让"两个租户同名用户"天然共存）。
- `t_session` 增加租户列并把唯一索引从 `session_id` 调为 `(com_code, session_id)`（今天靠前缀保证唯一，显式化后前缀就不再是正确性的一部分）。
- 迁移：老目录一次性 `mv`（或读时 fallback + 后台搬迁），保留一个版本的双读窗口。

**方案 B：ownerKey 改为不可逆哈希**（`sha256(comCode|sender)[:16]`）
- 收益：磁盘路径不再泄露用户标识（排查时多一步映射）；代价：可读性下降，且**不解决**"两套维度"的本质问题。适合与 A 叠加（A 的分层 + 哈希段作为目录名）。

**方案 C：会话文件按"租户 + 会话"存放（不按人）**
- `chat_history/<comCode>/<sessionId>.md`，把"谁拥有"交给 `t_session.sender`（DB 是权威）。
- 收益：目录数与人数解耦（不必为每个用户建目录、`ReadDir` 条目可控）；群聊天然支持（见角度二）。
- 代价：`sender` 与"文件位置"解耦后，"按人清理/导出"需要靠 DB 反查（多一次查询），换机器时目录结构变化较大。

> 取舍建议：**C 作为目标形态**（它同时解决问题 2 与角度二），A 作为过渡（改动小、可灰度）。要一起做的还有：`Begin` 显式接收 `comCode`；冲突处理沿用我们刚做的"不静默"（`ErrSessionOwnershipConflict` + notice）。**纠正一条此前的判断**：我在 `history-memory-review.md` 的 A1 里写"跨租户同名登录名会被视为同一归属"，在**当前 schema** 下不可达（登录名全局唯一）；准确的表述是"归属键缺少租户维度，是一颗**待触发的**地雷"。

## 角度二：群聊时历史写入后如何区分发言者

### 现状（代码事实）

- 记录格式：`## [<index>] <type>[:<title>] | <ts>` + 正文（`common/memory_record.go:1-16`）。
- `MemoryRecord{Index, RecordType, Title, TimeText, Content, CoversFrom, CoversTo}` —— **没有发言者字段**。
- 写入端 `appendTurn` 只写 type/title/正文，**不写谁说的**；`t_turn` 也**没有 sender 列**（`t_session.sender` 只是创建者）。
- 读取端 `buildHistoryItems` 只按 `role` 还原 → 模型看到的是 `user`/`assistant`，**无法区分多个人**。
- 归属守卫：`sender` 与创建者不一致 → **整轮丢弃**（`memory_service.go:154`）。
- `chat_type`(0 私聊/1 群聊)、`chat_channel`(1 WEB/2 飞书/3 微信/4 钉钉) **已存在于 `t_session`，但记忆链路完全没用到**（只在 `Begin` 里被写入）。
- 蒸馏提示词明确写"由同一单位下的**所有人共用**"（`distillation.go:38`），输入是 `user` 记录、**不分发言者**。

### 问题

1. **群聊从第二个人发言起就写不进历史**（静默丢弃）⇒ 群聊等于没有记忆；而且我们刚把"静默"改成"有 notice + 错误日志"，用户会看到"本轮未记入会话历史"的提示 —— 语义上更诚实，但功能仍然缺失。
2. 即便放开写入，**读回也丢失发言者** ⇒ 模型把多人的话当成同一人；`assistant` 回复会被算作"对所有人的回答"。
3. **蒸馏会混合多人的话**：`hasDurableSignal` 只看 `user` 记录、不区分人，多条个人陈述会被合并成"单位级事实"，且**无法按人删除**（隐私合规无法满足）。
4. **目录语义冲突**：`chat_history/<sender>/` 默认"一个会话属于一个人"，群聊里"会话属于谁"没有答案（现在是创建者，第二位发言人直接被拒）。
5. **未来 IM 渠道更严重**：飞书/微信接入时 `sender` 会是"我方服务号"而不是最终用户（`ChatController` 只从认证会话取 `LoginName`），所有 IM 用户的历史会落进同一个目录、共享同一份上下文。本仓库暂无 IM 接入，但常量已定义（`ChatChannelFeiShu` 等），属于"设计上必须提前留位"。
6. 群里"上下文可见范围"没有产品定义：是整群共享（所有人可见彼此的问答）还是仅对发言人可见？现在的实现在两种语义下都是错的。

### 方案

**1) 记录级发言者（最小改动、向后兼容）**
- 文件头扩展为 `## [n] <type>[:<title>] | <ts> | by:<sender>`；`MemoryRecord` 加 `Speaker string`。
- 解析：缺失 `by:` 的旧记录 → `Speaker=""`（视作"会话所有者"），不破坏历史文件。
- 装配：`user` 记录渲染为 `[张三] 正文`（或在消息前加一行 `（发言人：张三）`）；`tool`/`assistant` 不带。
- 蒸馏输入同样带发言人 → 可以在提示词里做"按下述发言人归属"的处理，或按 `chat_type` 直接跳过个人事实。
- `t_turn` 增加 `by_sender`（谁问的），`t_session.sender` 保留"创建者"语义。

**2) 归属模型从"单 sender"升级为"会话成员"**
- 私聊：保持单 `sender`（继续用 `ErrSessionOwnershipConflict`）。
- 群聊（`chat_type=1`）：归属判定改为"会话是否属于本租户 + 该用户是否在会话成员集合内"。这需要一张成员表（或在 IM 场景由外部系统给出群成员），当前代码里**没有任何成员模型**，属新增能力。
- 折中（无成员表时的过渡）：群聊的会话归属以"租户 + 群 id"为准，成员校验交给上游（IM 侧）。

**3) 目录策略按 chat_type 分支**
- `chat_history/<comCode>/<chatType==1 ? groupKey : sender>/…` 或直接采用角度一的方案 C（`<comCode>/<sessionId>.md`），让"会话文件"与"人"解耦 —— 群聊问题自然消解。

**4) 记忆作用域显式化**
- 群聊默认**只蒸单位级**（把 `chat_type` 变成蒸馏的硬约束，而不是靠提示词）。
- 若产品要"按人记忆"，则 `MEMORY.md` 分层：`单位级`（注入所有会话）+ `个人级`（仅注入该人的私聊），后者只从私聊蒸馏。
- 群里"某人的个人偏好"不应进入单位级文件（今天靠提示词兜，属于软约束）。

**5) 待产品回答的问题**：群聊上下文是否整群可见？群里能不能"@某人私下问"？群成员变动后历史可见范围如何收敛？—— 这三个决定成员模型与目录策略。

## 角度三：为什么需要蒸馏

### 现状与动机（代码事实）

1. **会话语义是隔离的**：`ReadRecords(session)` 只读当前会话的历史文件（`memory_service.go`），`t_session.chat_data` 指向唯一文件。⇒ 新会话、第二天回来、换个人来问，模型**什么都不知道**。
2. **跨会话唯一通道就是 `MEMORY.md`**：它是启动文档之一，**每次请求都注入**（`AgentDocMemory`，除 subagent/cron/heartbeat 外全注入），且体积有上限 `DistillMemoryDocMaxChars=12K rune`。
3. **注入预算有限**：历史回放受 `max_history_tokens`(默认 64K) + 窗口 + 系统提示预留三重约束，被裁掉的记录最终只剩摘要（只服务**该会话**）。
4. **成本**：把 2 万字符原文换成十几行事实，长期看省 token（蒸馏自己的输入上限 `DistillMaxInputChars=20000`）。
5. **成本之外的语义**：蒸馏提示词把作用域定成"**同一单位下所有人共用**"的长期事实（项目结构、口径、约定、被否决的方案、长期待办），并**明确排除**个人隐私与一次性内容（`distillation.go:37-54`）。
6. 为什么不用别的做法：RAG/向量检索对"口径/规范/字段口径"这类精确事实召回不稳，且要引入 embedding 与索引；结构化表要人工维护 schema。**文件 + LLM 蒸馏**的取舍是"让模型自己决定记什么"，代价是可控性差（见下）。

### 问题

1. **无 schema、每轮整体重写**：`replaceAutoMemory` 让模型输出"更新后的完整列表" ⇒ 同一事实被反复改写（抖动）、格式不稳定；一旦模型不听话，有"丢弃 >50% 则驳回"的安全阀，但那只是启发式。
2. **共享作用域 vs 个人输入**：输入是**个人对话**，输出进**单位共享文件**，靠提示词软约束"不要写个人隐私" —— 已被真实数据打破过一次（`default/MEMORY.md` 里出现过个人幸运数字/花/城市，人工清理过）。
3. **不可追溯**：事实行只有内容，没有来源会话/记录号/时间/置信度（水位注释只有 per-session 的 `watermarks=`），出问题无法回答"这条从哪来"。
4. **不可撤销**：一次糟糕的蒸馏会替换掉之前的事实（没有版本/回滚）。
5. **它是缓存杀手**：MEMORY.md 整体重写 → 见角度五。
6. **不可观测**：只有一行日志（`chat memory distill: … facts=1 updated=0 removed=0 migrated=0`），没有"这一轮具体增删改了什么"的记录。

### 方案

- **事实行带来源**：`- [2026-09-24|session_ab12#12-18] 事实内容`，或把 per-session 水位写到注释里（已有 `watermarks=`，扩展成 `watermarks=sess:index,start-end`），支持"按会话撤销/追溯"。
- **分区承诺**：把"人工维护区（模型只读）"与"自动区（模型重写）"显式化为对外契约（代码里已有 autoRegion 概念），并把该契约写进蒸馏提示词与文档。
- **作用域显式化**：`单位级` / `个人级` 两文件两提示词；个人级只在私聊蒸馏、只注入本人会话。群聊/IM 一律只蒸单位级。
- **版本与回滚**：写 MEMORY.md 前保留上一版（`.bak` 或 `MEMORY.md.<ts>`，保留最近 N 版），支持一键回滚；`prompt_service` 已有截断告警，可再加"蒸馏后事实数骤降"的告警（安全阀的观测补充）。
- **可观测**：每次蒸馏把 `added/updated/removed/watermark` 落库（新建 `t_memory_distill` 或写进 `t_turn` 旁路），便于按时间线审计。

## 角度四：压缩与蒸馏的触发点

### 现状（代码事实 + 数值）

| 动作 | 触发判定 | 阈值 | 限流/闸门 | 入口 |
|---|---|---|---|---|
| **压缩** | 有记录**掉出回放窗口**（`DroppedFrom/DroppedTo`）且条数/体积达标且摘要未超预算 | 条数 ≥ `CompactionMinRecords=4`；体积 ≥ `MinCompactionSrcRunes=400`；摘要总量 ≤ `MaxSummaryTotalRunes=12000` | `CompactionThrottle`：成功推进 5s / 失败 60s / 降级 120s→3600s 退避；全局槽位 `CompactionMaxConcurrent=3`；后台 120s 超时 | 每轮结束（成功/流式/中断） |
| **蒸馏** | 轮次节拍 或 内容积压 或 收尾 | `turns==6`(`DistillMinTurns`)；或 `turns>6 且 turns%10==0`(`DistillIntervalTurns`)；或 `PendingChars≥20000`(`DistillMaxInputChars`) 且 `turns%3==0`(`DistillCheckIntervalTurns`)；或 `closing` | 同上一行 + 本地预筛 `hasDurableSignal`（user 记录里出现路径/长数字/"以后/统一/口径/规范/约定/偏好…"）+ 预算门 `CalcMaintenanceBudgets` | 同上；`EndChatSession(closing=true)` **无生产调用点** |

补充事实：两者共用**一个**后台维护协程与**一个**全局槽位（`AcquireMaintenanceSlot`，非阻塞，拿不到直接放弃）；节流表与存储锁都是**进程内单例**；失败只记日志，下轮重试。

### 问题

1. **只在"下一轮到来"时触发** ⇒ 会话最后几轮的内容永远等不到（`EndChatSession` 没接），这是"尾部丢失"的根因；`closing` 通路已实现且有测试，但生产不触发。
2. **节拍以"轮次"为单位，与信息量无关**：闲聊 10 轮照样蒸（白烧一次 LLM 调用），而一轮长工具链可能已累积 2 万字符，却要等到 `%3` 的检查点。
3. **触发发生在"伤害之后"**：压缩的输入是**已经被裁出窗口**的记录 —— 它们从被裁那一刻起就不在 prompt 里了（信息真空 = 被裁 → 压缩成功之间可能好几轮）；蒸馏的水位钳制又会把压缩再推迟（`compactCeiling=watermark`）。
4. **门槛之间有空档**：压缩 4 条 / 400 rune 就够，蒸馏要 6 轮；4~5 条被裁时"可压但不可蒸"，压缩会先吞掉原文（现有钳制靠"先补蒸"兜，代价是压缩被推迟）。
5. **单点闸门 + 无队列**：全局并发 3，忙就直接跳过，没有任何重试/补偿 ⇒ 高并发或长任务堆积时维护会**长期饥饿**。
6. **多实例不安全**：`StorageLocks`（会话锁）与 `CompactionThrottle` 都是进程内；而历史文件与 `MEMORY.md` 是**磁盘共享**的 ⇒ 两个实例可能同时压同一会话（重复摘要）或同时重写 MEMORY.md（互相覆盖）。Redis 已在用，但没有用于这里的分布式锁。
7. **失败不可见**：预算装不下 / 冷却中 / 槽位忙 / 上游报错，全部只进日志；`backlog=` 也只在日志里，没有指标。
8. 触发完全依赖**当轮装配结果**；若当轮因别的原因失败（LLM 报错），维护就不会被调用（只有中断路径是这次刚补上的）。

### 方案

- **接上"收尾"通路**：`EndChatSession` 挂到"空闲超时扫描"或"手动结束会话"接口；这是 B1 的解法，也是"尾部丢失"的直接修复。若不想引入扫描器，最少也要在**客户端断开/turn 失败**时把 `closing` 语义用上（把这一轮当作"可能是最后一轮"，但要用更高的门槛避免白烧调用）。
- **触发维度换成"内容 + 时间"**：以 `PendingChars` 为主，把 `%10`/`%3` 从"是否触发"降级为"最快多久触发一次"（速率上限），例如 `pending >= 门槛 && sinceLastCheck >= 30s`。
- **预防式压缩**：在"回放预算使用率 > 阈值（如 80%）"时就压缩，而不是等记录真的掉出窗口；或在装配前做一次"预判定"。
- **维护改成可重试任务**：per-session 的 pending 标记 + 退避重试（而不是"这轮不行就等下一轮"），并在 Redis 上加 `SetNX` 的会话级锁，保证多实例下同一会话只有一个维护者。
- **指标化**：把 `skip reason / backlog / queue wait` 做成计数器或表，配告警（"某会话 backlog 持续 > N 轮"）。
- **明确一次"压缩 vs 蒸馏"的优先级**：现状是"先蒸后压 + 水位钳制"，建议把这条规则写成不变量并有测试锁住（避免后续改动再次让压缩吞掉未蒸原文）。

## 角度五：system prompt 的缓存（前缀缓存）如何做

### 现状（代码事实）

**段落顺序**（`assembleSystemPrompt`，`context_assembler.go:376-530`）：

```
[1] 启动文档 ×7:AGENTS → SOUL → IDENTITY → USER → TOOLS → BOOTSTRAP → MEMORY   ← 第 7 个是 MEMORY
[2] Available Skills         (随本轮意图门 gate 变化)
[3] Available Tools          (随 gate 变化;由实际下发的 tools 派生)
[4] Skill 正文(命中技能的 SOP)(随 gate 变化)
[5] Bootstrap Context Notice (仅当有截断时出现)
── 固定尾巴(不受预算截断)──
    ## 当前时间   ← 每轮都变
    ## 输出语言   (常量)
    ## 工具调用   (常量)
── 由 buildSystemMessage 追加 ──
    ## 历史摘要   ← 压缩/合并时会变(位置在"当前时间"之后!)
```

消息序列 = `[system] + [历史(append-only)] + [本轮 user]`（`AssembleContext`）；工具 schema 在请求体 `tools`（不在 messages）。

代码里已经有前缀缓存意识（"放在最末(而非开头)是为保住前缀缓存" —— 指 `## 当前时间`）。

### 问题（按破坏力排序）

1. **MEMORY.md 排在第 1 部分的末尾**，而它每次蒸馏都被**整体重写** ⇒ **一次蒸馏就让"从 MEMORY 段开始"的所有后续 section 的缓存全部失效**（技能目录、工具清单、技能正文、通知、尾巴）。这是当前**最大的缓存破坏源**，也可能是最容易修的。
2. **`## 当前时间` 排在"历史摘要"之前** ⇒ 虽然自身在尾部（思路正确），但它每轮都变，于是**把它后面的摘要段每轮都打失效**（摘要在会话内本可以不怎么变）。**顺序 bug**：易变的应最后。
3. **Available Skills / Available Tools / Skill 正文随 gate 变化**：同一 agent 的不同问题会切技能 ⇒ 第 2~4 段不稳定。它们排在启动文档之后，所以"前 4 段稳定"这一假设**只在"启动文档前 4 个"口径下成立**（AGENTS/SOUL/IDENTITY/USER 确实稳定）。
4. **Bootstrap Context Notice** 只在截断时出现 → 出现/消失会打断段序（低频，可接受）。
5. **压缩会替换历史摘要** ⇒ 中频失效（每 ~10 轮一次），但因为它和 MEMORY 都在尾部区，失效范围可控。
6. **工具循环内 `FitMessages` 从头部裁剪历史** ⇒ 同轮后续请求的 messages 前缀从第一条历史起就变（system 仍命中）。这是必要的裁剪，但会让"同轮多次上游调用"的缓存收益下降。
7. **无法观测**：代码里没有记录 system prompt 指纹，也没读上游返回的缓存命中字段（DeepSeek 的 `prompt_cache_hit_tokens` / OpenAI 的 `cached_tokens`）⇒ 优化效果无法验证。
8. **顺序约束只靠注释**：段落顺序是"稳定→易变"的设计意图，但没有任何类型或测试强制；后续随手加一段就会破坏它（这次分析就是靠读注释才还原出意图的）。

### 方案

**1) 重排段落（低成本、收益最大）**

```
[稳定前缀] 启动文档 AGENTS/SOUL/IDENTITY/USER/TOOLS/BOOTSTRAP
          → Available Skills → Available Tools → Skill 正文
[低频变化] 历史摘要 → Bootstrap Context Notice
[高频变化] MEMORY.md(自动区) → ## 当前时间 → ## 输出语言 → ## 工具调用
```
- 预期收益：蒸馏只失效"MEMORY 及其后"（约等于零），压缩只失效"摘要及其后"；`## 当前时间` 移到最后后，**会话内除压缩外 system 前缀完全稳定**。
- MEMORY.md 进一步拆分：**人工区（几乎不变）放稳定前缀**，**自动区（模型重写）放最末** —— 蒸馏就彻底不影响任何稳定段。

**2) 把顺序变成工程约束**
- `SystemPrompt` 增加两个字段：`StablePrefix` / `DynamicTail`（或给 section 打 `Volatility` 等级），拼接顺序由类型保证；加一个单测断言"稳定段必须先于易变段"（例如断言 `indexOf(MEMORY) > indexOf(Available Tools)`）。
- 现有的"预算记账与渲染共用常量"是个好先例，可以沿用同样的思路（把顺序也变成单一来源）。

**3) 减少中频变化**
- 技能/工具目录：同一 agent 的"全量清单"是稳定配置 —— 可以只列**全量能力**（不带本轮可用性），把"本轮可用"交给请求体 `tools`（已经这么做了）。真正随 gate 变的是"Skill 正文"；可考虑把正文放最后（代价：提示效果要重新评估）。
- MEMORY.md/摘要的注入形式评估：是否可改为"最后一条 system 之外的 user 消息"（供应商兼容性已有一条注释说明为何折进 system —— 保持现状，只调顺序）。

**4) 可观测**
- 记录每轮 `system_prompt_hash` + 各段长度，并在响应里读上游的缓存命中 token 数，落到日志/表；有了基线才能验证"重排"到底省了多少。
- 加一条监控：同一会话连续两轮的 `system_prompt_hash` 变化原因（配置/蒸馏/压缩/时间）—— 这是排查"缓存突然不命中"的唯一办法。

**5) 跨会话复用**
- 同一 (租户, agent, scope) 的所有会话共享前 4 段 ⇒ 命中率天然高；要保住它，就要保证"配置不变即字节不变"（当前 `MEMORY.md` 与摘要按会话不同，不影响前缀；但**蒸馏重写 MEMORY.md 会打破同一 agent 所有会话的前缀** —— 这是重排的另一个理由）。
